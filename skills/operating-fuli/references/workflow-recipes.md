# FULI Agent workflow recipes

Use these as sequencing hints only. Always call `list_agent_interfaces` and inspect the current tool schema first.

| Intent | Read before | Mutation | Verify after |

| Move an external-knowledge connection between projects | `list_external_knowledge_bindings` | `update_external_knowledge_binding_targets` | `check_external_knowledge_binding`, then `retrieve_external_knowledge_binding` or `sync_external_knowledge_binding` when requested |
| Create an external-knowledge connection | `list_external_knowledge_connectors`, `discover_external_knowledge_sources` | `create_external_knowledge_binding` | `check_external_knowledge_binding` |
| Change how knowledge conflicts are handled | `get_external_knowledge_conflict_policy` (without `personalProjectId`: the default and each project's own choice) | one project: `update_external_knowledge_conflict_policy` (`mode: null` returns it to the default); every project without its own choice: the same tool without `personalProjectId`, only when the person asks for the default | `get_external_knowledge_conflict_policy` with the project's ID: `mode` and `source` (`project` or `default`) |
| Change capture behavior (global, client or project mode; "这个项目以后别记了" is `recordProjects` with the current project's ID) | `get_capture_policy` with `projectPath` | `update_capture_policy` (with the current `taskContextToken`) saves nothing and returns `preview` and `confirmUrl`: show both word for word; the person confirms or cancels in the FULI console. No Agent call can complete it | `get_capture_policy` after the person says they confirmed |
| See or restore old data FULI kept (backups, "之前的数据还在吗", how much space FULI takes) | `read_old_data`, then with the item's `id` for its files and `path` for one text file | the person asks to restore a `restorable` item: `run_delegated_action` `POST /api/old-data/:id/restore` (settings permission; FULI restarts). Deleting now stays the person's in 设置 › 系统 › 存储 | `read_old_data`: a new item holds the store as it was before the restore |
| Pause or resume recording of this session ("这次别记" / "继续记") | none | `update_capture_policy` with only `sessionPaused` and the current `taskContextToken`, at once and without confirmation | end the reply with the returned `agent_receipt` |
| Turn FULI off or on for this session | none | no Agent tool: tell the person to type `/fuli stop` or `fuli stop` (`start`, `restart`, `status`) | the hook's answer is shown to the person |
| Check whether FULI works and what needs fixing, including a client that needs an update or a restart to load one (体检) | the `policy-and-health` workflow names the read-only doctor route, `GET /api/system/doctor` on the local console | its 「自动修复」 (reconnecting clients that were connected before; on Windows, limiting a `data_dir_shared` data directory to the person's account and SYSTEM) is `run_delegated_action` with `POST /api/system/doctor/repair` when the person asks (settings permission); otherwise tell them what the console banner lists. Items with `fix: person` (confirming a data format migration, restarting client sessions, trusting Codex's hooks in `/hooks`) stay theirs. An `npm_copy_installed` info item (only on the desktop app) names an npm installation of FULI beside the app: the app already runs the shared data and pointed the connected clients at itself; `data.copies[].shellCommands` are the bare commands a terminal still answers with that older copy. The console offers 「卸载」 for it; you remove it only with the person's own words (`agent_relayed` `POST /api/system/npm-copies/uninstall`), and closing its console notice is the delegable settings route `PUT /api/system/npm-copies/notice`. Whether terminals run the desktop app's own `fl`/`fuli` is `GET /api/system/cli-path`, switched only with the person's own words (`agent_relayed` `PUT /api/system/cli-path` `{ enabled }`) (turning it off takes out exactly the PATH entry and scripts FULI added). A client session moves to a newly installed FULI on its own once it is idle, so a `sessions_outdated` item names only sessions started before that hand-over existed, and each needs one restart. Servers from a FULI older than its process records are found in the operating system's process list instead: one `sessions_outdated:other:unknown` item with `runningVersion: null`, a `count`, no `sessions` and `since` the oldest start. Such a session also gets one task-entry notice; when its connection predates the task-entry contract, the notice says the hook token may not be readable there, and a task-context refusal to an older connection names its version and asks for a reconnect. Its `sessions` are what the console's 「打开」 links open when the person clicks them, never something to open for them. A `data_format_waiting` item with `lastSeenAt` is the graph's answer from before it went idle: until it is confirmed, every FULI write to the graph fails with `data_format_read_only`. `unchecked` lists what was not checked, never a healthy result (`data_dir`: the data directory's ACL could not be read); `uncheckedReasons` says why (`graph_format`: `graph_sleeping` or `graph_not_answering`; `hook_trust:codex`: `codex_missing`, `codex_timeout` or `codex_error`, when FULI could not read Codex's app-server `hooks/list`; a `hook_trust_untrusted` item with `fix: person` reports FULI hooks that are not all trusted, which the person trusts in Codex's `/hooks`; `sessions`: `process_list_unavailable`, when the process list could not be read within 5 seconds, so nothing is said about unrecorded servers; `transcript_format:<clientId>`: `no_transcript` when a connected client has no transcript changed in the last 7 days, or `transcript_unreadable`; a `client_format_changed` item with `fix: person` reports a connected client whose newest transcript FULI's parser read under half of (at least 5 lines, counts only in `data.recognized` / `data.total`), so capture from it may miss records until FULI is updated; `clients`: `client_detection_unavailable`, because agent-installer, which reads which clients are installed and whether FULI is in them, could not run, so nothing is known about any client) | the person's banner after they repair; never confirm a migration, restart a session or trust hooks for them |
| See when a project appeared and who changed its profile | the `projects` workflow names the console read `GET /api/personal-projects/:projectId/history`; no Agent tool reads it, so send the person to the project's overview (创建于, 修改记录) | none: `upsert_personal_project` records each real change by itself, and the record is append-only | the overview's 修改记录 |
| Find out why FULI failed (a hook said FULI was unavailable, a tool or console request errored, the Provider did not start) | none | none: `fuli_call("read_diagnostic_events", …)` is read only; filter by `from`/`to`, `component` (`hook`, `http`, `provider`, `mcp`), `level` and `code`, page with `cursor`. With FULI's console or MCP down, `fuli diagnostics` on this computer reads the same files | report events with time, component, operation and code, plus `truncated`/`truncatedBy`, `sourcesUnavailable` and `notCovered`; an empty answer is not proof of health |
| Add or change durable knowledge | the narrowest knowledge search/read tool | the matching knowledge submission or decision tool | read the exact item and confirm scope/version; a confirmed keyed value (URL, port, command, owner) ends the older value of the same subject and relation by itself, and only a person's restore takes an ended one back (capturing the same words again writes a new current item and leaves the ended one as history); a confirmed preference ends the current one with the same `preferenceKey` and scope, with no restore (the person states the old one again as a new version); items listed `possibly_outdated` wait for the person; a duplicate of a current item (same words or a longer list of the same checks that was said last, same type and scope) is merged into one current item automatically, and only a person's restore of the merged copy in the console splits it back |
| Send a kind of work to its own project from now on ("以后 iDev 工时都交给 X") | none | `register_standing_assignment` `preview` writes nothing and returns one `restatement`: ask the user once; after a clear yes, `confirm` with the same input and `confirmationDigest` | the result says registered and assigned, not executed; do the current request, if any, as usual |
| Correct or end such a rule ("工时以后交给 ops" / "iDev 不用再交给 X 了") | none | the same tool with `change` `retire`, `reassign` (`projectName`, `leadAgentId`; default that project's lead) or `edit_terms` (`addTerms`, `removeTerms`), naming the assignment by one of its terms in `term`: `preview`, ask once, `confirm` with the digest. Removing every term is refused; retire instead | the result's `assignment`; the project's own lead is unchanged. The person can also do it in the local console (loopback only) |
| Pause everything (or one FLA's or one project's) and later bring it back ("全部暂停" / "恢复") | `list_work_surfaces` with the filter the person named | `pause_work_surfaces` with that filter and the current `taskContextToken`; later `resume_work_surfaces` with its `pauseId` (default: the latest pause) | each item's `result`: `paused`/`already_off`, then `resumed`/`left_off`; `restart_required` items need their owner to restart them with `detail.command`; `list_work_surfaces` again |
| Turn work you keep repeating into your own workflow | `list_agent_workflows` (is there one already?) and `list_workflow_candidates` for a candidate that repeated across sessions | `propose_agent_workflow` with the current `taskContextToken`, `name`, `purpose` and `candidateId` or `steps` (`workflowId` to propose a change): it waits for the person | tell the person it waits on your home page's 工作台 tab (they decide there, or ask you to record their decision with `run_delegated_action`); once active, `read_agent_workflow` when a task needs it and `record_agent_workflow_run` after following it |
| Make a console change for the person that has no tool of its own (a setting, an occupation, the project hierarchy, stopping a service, …) | `list_agent_interfaces`: the entry must be `agent_delegable` or `agent_delegable_off`; read the current record | `run_delegated_action` with `taskContextToken`, the exact `route`, `params`, `body` and `reason`; `delegation_category_off` means the person turns it on in 设置 › AI 权限 | re-read the record; put `delegation_receipt.markdown` (with its undo) in the reply |
| Record a decision the person made in chat (an attention reply, a Tonborg vote, a conflict ruling, a confirmation, a Jefa acceptance, their 「我」 name) | `list_agent_interfaces`: the entry is `agent_relayed`; ask the person in chat and read the current record | `run_delegated_action` as above plus `personWords`, their exact words that decide it; `person_words_not_found` means FULI did not find them in the message that began your task, their newest 5 saved messages of this session, or an answer they picked in the client's own question card during this task: ask again, never rephrase | re-read the record; put `delegation_receipt.markdown` (it quotes their words) in the reply |
| Go through Tonborg's unsure items in 待决策 with the person (「让 Tonborg 给你解释」) | `list_tonborg_questions` (titles and guesses), then one `decisionId` for the item; read the item with your knowledge tools (Tonborg's reason stays in the console); above 5 items ask how many to hear first | the person decides in chat: `answer_tonborg_question` with their exact `personWords` (`edit` with `newText`) | `list_tonborg_questions` again: the answered item is gone; put `delegation_receipt.markdown` in the reply |
| Show the person the Agent replies FULI kept by mistake (待决策 › 之前误存的 Agent 回复) | `list_reply_echoes` (total, short text, signals) | the person drops them: their click on 全部丢掉, or `run_delegated_action` `POST /api/knowledge/reply-echoes/drop` with the listed `items` and their exact `personWords` | `list_reply_echoes` again: the dropped items are gone; `POST /api/knowledge/reply-echoes/restore` undoes it; put `delegation_receipt.markdown` in the reply |

For the external-knowledge move example, prefer updating the existing binding targets. Do not delete and recreate the binding merely to change project membership: recreation can lose revision history, connector state, and audit continuity.

Always inspect the complete `targets` array, not the legacy first-target aliases (`target`, `mode`, `sync`). When a user excludes project B, preserve other authorized targets, remove B explicitly, verify the saved array, and synchronize only the requested target/project. An unscoped sync covers every syncable target.

Pass the last-read `targetsVersion` as `expectedTargetsVersion` when changing targets. On `external_knowledge_conflict` or `external_knowledge_busy`, re-read after the other operation completes; do not replay a stale target array. The registry serializes mutations across console/MCP processes; an interrupted process releases its reservation automatically.

Bole and Tonborg are provisioned by the Provider as fixed native roles: `recruit_employee` never creates or reactivates them (`system_managed_employee`), but once active it edits the projects they manage like any employee scope (`management` with `replaceAssignments` and the last-read `expectedAssignmentsVersion`; `assignment_scope_conflict` means re-list first). Astro (`assistant`) works globally and takes no projects. Re-list the template to verify `management` and `managedProjects`. Inspect staffing through the Project Agent read tools.

Every Agent has a person-like nickname unique in its personal space. When recruiting or creating one, put the job in its occupation and responsibility, not its `displayName`: a job-title name or none is replaced by a generated name. Right before proposing a new Agent's `displayName` (`recruitmentProfile` or `upsert_project_agent`), call `get_agent_naming_style`: when the person saved a style (FLA 取名偏好), propose a name in it; when it returns `null`, omit `displayName`. A given name another Agent uses is refused with `agent_name_taken` and free generated names, before anything is written: propose another in the same style, or use one of them. If you cannot find a free name, tell the person; never reuse a taken one. Only the person edits the style, on their home page (「我」, `/preferences`) beside Bole, where it starts as FULI's own naming rule; leaving or restoring that default saves no style (`explain_settings` gives the link). Changing a style never renames existing Agents, and renaming an existing Agent to a taken name is refused the same way. Never rename an existing Agent on your own; a read may return `nameSuggestion` for the person to accept. When the person asks to rename any Agent, FULI's own roles included, call `rename_project_agent` (`displayName`; `null` gives Jefa, Bole, Tonborg or Astro its built-in name back): only the shown name changes, identity stays the `agentId`, and a renamed role still answers to its built-in name, which no other Agent may take. An Agent's avatar (a re-rolled drawing, an uploaded picture, or the default) is the person's choice; change it only when they ask, with `run_delegated_action` (`PUT /api/agent-avatars/:agentId`, organisation permission). The person's own home works the same way: their picture and what FULI calls them are set only there, on this computer (`PUT /api/person-profile` is `agent_relayed`: change it only with the person's exact words from chat; no Agent tool reads the picture). When they said how to be called, the task entry's `context.address_as` carries it: address them by it in replies, and never ask for it, guess it or write it into knowledge. Without it, keep your usual neutral address.

Runtime settings, the doctor's repair, adding or removing a hand-described client, marking a blocked task cleared and the other `agent_delegable` entries are made for the person with `run_delegated_action` (see SKILL.md). Clear a block only after you fixed it, with `reason` saying what you did; the history names you, not the person. Confirming a block FULI shows as probably resolved (「确认已解除」) is the person's own click. The following controls are deliberately local-user-only unless the current interface catalog says otherwise:

- Agent-access policy and the AI permissions themselves (设置 › AI 权限)
- model API keys, and listing the models an endpoint offers (the model dialog's 模型 picker sends the saved key there): when the person asks you to connect a model, the key goes on stdin into `fuli models set-key <secretRef> --endpoint <url>`, never through a tool, and is sent only to that origin; list the endpoint's models yourself with the key they pointed you to (SKILL.md, AI permissions)
- the first-run guide's client steps (「开始使用 FULI」: 一键接入 the AI clients found on this computer, 开机启动 in the Windows desktop client): when the person wants to connect more clients or change start at login, point them to 设置 › 客户端 「一键接入」 (and the tray menu 「开机时启动」 for start at login); closing the guide and answering where FULI records are `agent_relayed` with their words
- permanently deleting knowledge or a fact (「删除…」, rec#11 D-88): suggest the person opens the item in the console, where 「删除…」 is one click away on the item, its page and each of its facts, and the dialog offers 取消 / 导出并删除 / 确定删除; preview and full-text export are also console-only, with no Agent tool
- the 诊断包 (diagnostics bundle, `GET /api/system/diagnostics`): a console-only read from this computer; it carries this computer's redacted logs and environment, so suggest the person opens 设置 › 系统 › 诊断包 (or the desktop tray's 「导出诊断包…」), previews it and exports it; never fetch it for them

Explain the precise UI action when one of these boundaries blocks the request. Never work around it through direct HTTP, storage, browser scripting, or a shell command.
