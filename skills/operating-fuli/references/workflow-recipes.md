For the external-knowledge move example, prefer updating the existing binding targets. Do not delete and recreate the binding merely to change project membership: recreation can lose revision history, connector state, and audit continuity.

Always inspect the complete `targets` array, not the legacy first-target aliases (`target`, `mode`, `sync`). When a user excludes project B, preserve other authorized targets, remove B explicitly, verify the saved array, and synchronize only the requested target/project. An unscoped sync covers every syncable target.

An Agent cannot create or discover through an MCP stdio command, or name a credential (`tokenEnv`, `headerEnv`) for an MCP or retrieval endpoint it chose, point either at a loopback URL, or connect a custom code module: all are refused with `local_user_only`. Ask the person to add that connection on the console's 连接 page, then work with the binding it creates (check, sync, retrieve, targets). Notion and Feishu connections, and an MCP endpoint that takes no credential, stay available.

Pass the last-read `targetsVersion` as `expectedTargetsVersion` when changing targets. On `external_knowledge_conflict` or `external_knowledge_busy`, re-read after the other operation completes; do not replay a stale target array. The registry serializes mutations across console/MCP processes; an interrupted process releases its reservation automatically.

Bole and Tonborg are provisioned by the Provider as fixed native roles: `recruit_employee` never creates or reactivates them (`system_managed_employee`), but once active it edits the projects they manage like any employee scope (`management` with `replaceAssignments` and the last-read `expectedAssignmentsVersion`; `assignment_scope_conflict` means re-list first). Astro (`assistant`) works globally and takes no projects. Re-list the template to verify `management` and `managedProjects`. Inspect staffing through the Project Agent read tools.

Every Agent has a person-like nickname unique in its personal space. When recruiting or creating one, put the job in its occupation and responsibility, not its `displayName`: a job-title name or none is replaced by a generated name. Right before proposing a new Agent's `displayName` (`recruitmentProfile` or `upsert_project_agent`), call `get_agent_naming_style`: when the person saved a style (FLA 取名偏好), propose a name in it; when it returns `null`, omit `displayName`. A given name another Agent uses is refused with `agent_name_taken` and free generated names, before anything is written: propose another in the same style, or use one of them. If you cannot find a free name, tell the person; never reuse a taken one. Only the person edits the style, on their home page (「我」, `/preferences`) beside Bole, where it starts as FULI's own naming rule; leaving or restoring that default saves no style (`explain_settings` gives the link). Changing a style never renames existing Agents, and renaming an existing Agent to a taken name is refused the same way. Never rename an existing Agent on your own; a read may return `nameSuggestion` for the person to accept. When the person asks to rename any Agent, FULI's own roles included, call `rename_project_agent` (`displayName`; `null` gives Jefa, Bole, Tonborg or Astro its built-in name back): only the shown name changes, identity stays the `agentId`, and a renamed role still answers to its built-in name, which no other Agent may take. An Agent's avatar (a re-rolled drawing, an uploaded picture, or the default) is the person's choice; change it only when they ask, with `run_delegated_action` (`PUT /api/agent-avatars/:agentId`, organisation permission). The person's own home works the same way: their picture and what FULI calls them are set only there, on this computer (`PUT /api/person-profile` is `agent_relayed`: change it only with the person's exact words from chat; no Agent tool reads the picture). When they said how to be called, the task entry's `context.address_as` carries it: address them by it in replies, and never ask for it, guess it or write it into knowledge. Without it, keep your usual neutral address.

LAN roundtable nearby pairing (rec#127; `lan_roundtable` permission, off until the person turns it on): with their go-ahead, an Agent may turn discovery on with `run_delegated_action` `POST /api/peer/nearby { on: true, name? }` (or `fuli peer nearby on [--name NAME]`) on each computer and start a pairing; it tells devices on that network that the computer runs FULI, under the name given or `FULI` plus four fingerprint characters (never the computer's own name). It turns itself off after a pairing or 30 minutes (`nearby.ended` says why, including `discovery_failed` with its reason); turning it on again while on keeps that end. Read `GET /api/peer` (`nearby.devices`: name, `fingerprint`, `paired`), then start `POST /api/peer/nearby/pair { fingerprint }` (`fuli peer pair <first 4+ characters>`). Both computers then show the same `nearby.pairing.code` for 2 minutes. Never confirm it, read it out as compared, or type it for the person: `POST /api/peer/nearby/confirm` is `local_user_only`. The person ticks 「两台电脑的 6 位数字一样」 and clicks 确认 on each computer, or runs `fuli peer confirm <the code shown on the other computer>` there; a code that differs cancels the pairing (`code_mismatch`). `POST /api/peer/nearby/cancel` stops or refuses a request. Every pairing handshake is counted on each computer (`nearby.attempts`: 5 per 10 minutes, 10 per 24 hours); off and on, a restart or an Agent never clears it. At the limit (`nearby.limited`) tell the person that many attempts can mean someone is trying to pair uninvited; they may wait, or clear it themselves on that computer as a deliberate second step (「是我自己在试…」 then 确认清零, or `fuli peer nearby clear-attempts`; `POST /api/peer/nearby/attempts/clear` is `local_user_only`). `nearby.pairing.state` `waiting` means this computer trusts the other but it has not connected yet; only after its first connection is it `paired` (or `trust_withdrawn` when it never connects). When `coordinator.listenFailure` is set nothing listens (its address is gone); tell the person to turn the LAN roundtable off and on. Nobody picks the coordinator: the computer that already coordinates others keeps it, otherwise the one picked from the list. Pairing shares the leads of up to 8 projects the other computer reports having too: when the person confirms the code (on each computer), and on the computer that joins with an invitation (the screen and `fuli peer join` say so first), FULI shares once per paired device the lead of every project here whose own repository the coordinator reports the other computer also registered (never archived, temporary or session-only ones; a reference source never counts), with the lead's first allowed wake client and the folder only when a checkout is known and maps to that project. It waits until the coordinator holds both computers' digests under its current key (up to about 3 minutes). It shares nothing when more than 8 match (`skipped: too_many`) or when the group has any other computer (`skipped: group`; a share reaches every device in the group): then the person uses 「共享这 N 个相同的项目」, told that the other computers can ask those leads too (`groupSize` > 2). It never changes or removes an existing share, and a project the person shared or unticked since the pairing keeps their choice. `GET /api/peer` `autoShared` lists what each pairing shared or why it shared none, and the card names them (「配对后已共享：…」); `autoSharePending` is true while a pairing still waits for that answer. Known limit: on a computer that joined (a member), both the matching projects and who else is in the group come from the coordinating computer, which the member cannot check; a dishonest coordinator could hide other members, so the member's card says the other computer decides who else is in the group and anything unsure can be unticked. The confirm step stays `local_user_only`. `shareable` is short: the shared projects and the suggestions; `shareable[].sameProjectOn` names paired computers whose project has the same own repository (matched on the coordinator with a key only the paired group has; a device never sees another's digests), and `knownFolder` a folder here whose Git origin is that repository (null: ask the person). Suggestions not shared yet (the coordinator of an invitation pairing, pairings from before this) are shared only by the person: 「共享这 N 个相同的项目」 or ticking them. Other projects are found by name with `GET /api/peer/shareable?query=<text>&limit=20` (`{ projects: [{ projectId, projectName }], more }`, no team reads) and read whole with `GET /api/peer/shareable/<projectId>` before adding them; nothing is shared until saved with `PUT /api/peer/shares` (the full list). A share list the coordinator did not get fails with `share_not_published` and shows in `lastPublish`.

Guest links (访客链接, rec issue 133): someone on the same network whose computer has no FULI asks one project, read-only, from their own AI client. The person makes a link on the project page (生成: 1, 7 or 30 days, 7 by default) and copies one sentence for any AI that can run commands; the token (`fgl_…`) is shown only in that dialog, and FULI keeps only its SHA-256. While at least one link is live, FULI listens on port 2729 of this computer's private and carrier-grade NAT (100.64.0.0/10) addresses, apart from the console; with none it does not listen. A holder sends the token only as `Authorization: Bearer fgl_…` and reaches exactly `GET /guest/1/card` (project name, its lead's name and responsibility, expiry, how to ask) and `POST /guest/1/search { queries: [1-4] }` (the same narrowed search as a paired computer's visiting assistant: that project's own confirmed, current, normal-sensitivity knowledge, at most 8 items per query and 16 KB, no local paths, recorded per attempt under `guest:<linkId>`, 30 per 10 minutes and 300 a day). A holder never reaches the console or `/api/*`, another project, preferences, FLA memory, pending, historical, private or restricted knowledge, or any write; a link only asks, and requests that run work are not offered. A missing, wrong, expired or revoked token gets the same `401`; 10 failures from one address in 10 minutes give `429`. The link works only on the same network and travels there unencrypted.

Runtime settings, the doctor's repair, adding or removing a hand-described client, marking a blocked task cleared and the other `agent_delegable` entries are made for the person with `run_delegated_action` (see SKILL.md). Clear a block only after you fixed it, with `reason` saying what you did; the history names you, not the person. Reporting `running` or `queued` with `record_project_agent_task_activity` and your `taskContextToken` makes that clear for you first, only when the report itself would pass (same permission, same record; the result's `blockerCleared` says so), and with Organisation off nothing is cleared and the refusal names the switch. Confirming a block FULI shows as probably resolved (「确认已解除」) is the person's own click. The following controls are deliberately local-user-only unless the current interface catalog says otherwise:

- Agent-access policy and the AI permissions themselves (设置 › AI 权限)
- model API keys, and listing the models an endpoint offers (the model dialog's 模型 picker sends the saved key there): when the person asks you to connect a model, the key goes on stdin into `fuli models set-key <secretRef> --endpoint <url>`, never through a tool, and is sent only to that origin; list the endpoint's models yourself with the key they pointed you to (SKILL.md, AI permissions)
- the first-run guide's client steps (「开始使用 FULI」: 一键接入 the AI clients found on this computer, 开机启动 in the Windows desktop client): when the person wants to connect more clients or change start at login, point them to 设置 › 客户端 「一键接入」 (and the tray menu 「开机时启动」 for start at login); closing the guide and answering where FULI records are `agent_relayed` with their words
- permanently deleting knowledge or a fact (「删除…」, rec#11 D-88): suggest the person opens the item in the console, where 「删除…」 is one click away on the item, its page and each of its facts, and the dialog offers 取消 / 导出并删除 / 确定删除; preview and full-text export are also console-only, with no Agent tool
- the 诊断包 (diagnostics bundle, `GET /api/system/diagnostics`): a console-only read from this computer; it carries this computer's redacted logs and environment, so suggest the person opens 设置 › 系统 › 诊断包 (or the desktop tray's 「导出诊断包…」), previews it and exports it; never fetch it for them

Explain the precise UI action when one of these boundaries blocks the request. Never work around it through direct HTTP, storage, browser scripting, or a shell command.
