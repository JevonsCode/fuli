Single-Skill paired evaluation: to check whether one saved workflow version actually helps a task, run `fuli-skill-eval --store <agent-workflows.sqlite> --list` (installed FULI; in a source checkout use `npm run measure:skill-paired --`), then repeat with `--workflow-id` and `--mode deterministic` (CI seam) or `--mode opencode --model <provider/model>` (real isolated client that sends model requests); details and the result fields are in `acceptance/skill-paired-eval/README.md`. The OpenCode adapter grades response markers in the assistant answer and keeps the full client transcript as evidence.

For the external-knowledge move example, prefer updating the existing binding targets. Do not delete and recreate the binding merely to change project membership: recreation can lose revision history, connector state, and audit continuity.

Always inspect the complete `targets` array, not the legacy first-target aliases (`target`, `mode`, `sync`). When a user excludes project B, preserve other authorized targets, remove B explicitly, verify the saved array, and synchronize only the requested target/project. An unscoped sync covers every syncable target.

An Agent cannot create or discover through an MCP stdio command, or name a credential (`tokenEnv`, `headerEnv`) for an MCP or retrieval endpoint it chose, point either at a loopback URL, or connect a custom code module: all are refused with `local_user_only`. Ask the person to add that connection on the console's 连接 page, then work with the binding it creates (check, sync, retrieve, targets). Notion and Feishu connections, and an MCP endpoint that takes no credential, stay available.

Pass the last-read `targetsVersion` as `expectedTargetsVersion` when changing targets. On `external_knowledge_conflict` or `external_knowledge_busy`, re-read after the other operation completes; do not replay a stale target array. The registry serializes mutations across console/MCP processes; an interrupted process releases its reservation automatically.

Bole and Tonborg are provisioned by the Provider as fixed native roles: `recruit_employee` never creates or reactivates them (`system_managed_employee`), but once active it edits the projects they manage like any employee scope (`management` with `replaceAssignments` and the last-read `expectedAssignmentsVersion`; `assignment_scope_conflict` means re-list first). Astro (`assistant`) works globally and takes no projects. Re-list the template to verify `management` and `managedProjects`. Inspect staffing through the Project Agent read tools.

Every Agent has a person-like nickname unique in its personal space. When recruiting or creating one, put the job in its occupation and responsibility, not its `displayName`: a job-title name or none is replaced by a generated name. Right before proposing a new Agent's `displayName` (`recruitmentProfile` or `upsert_project_agent`), call `get_agent_naming_style`: when the person saved a style (FLA 取名偏好), propose a name in it; when it returns `null`, omit `displayName`. A given name another Agent uses (or a built-in role's own name) is refused with `agent_name_taken`, who uses it and in which projects (`used by: …`, also as `used_by`), and free generated names (`free_names`), before anything is written (another FLA's 原名 is taken for 30 days: its `used_by` entry gives `former_name` and `free_from`); the graph itself keeps names unique, so two hires racing for one name never both get it: propose another in the same style, or use one of them. If you cannot find a free name, tell the person; never reuse a taken one. Only the person edits the style, on their home page (「我」, `/preferences`) beside Bole, where it starts as FULI's own naming rule; leaving or restoring that default saves no style (`explain_settings` gives the link). Changing a style never renames existing Agents, and renaming an existing Agent to a taken name is refused the same way. Never rename an existing Agent on your own; a read may return `nameSuggestion` for the person to accept. When the person asks to rename any Agent, FULI's own roles included, call `rename_project_agent` (`displayName`; `null` gives Jefa, Bole, Tonborg or Astro its built-in name back): only the shown name changes, identity stays the `agentId`, the old name goes into the Agent's name history (records carry `nameHistory`, and `formerName` for 30 days: say 「原名 …」 when you introduce it), and a renamed role still answers to its built-in name, which no other Agent may take. FLAs that shared a name before names were unique keep it, and everything works, until the person settles it: `GET /api/project-agent-name-fixes?personalSpaceId=…` lists each shared name, who keeps it, each other FLA's new name and why (`keep=<agentId>` to let another keep it). Show that to the person when shared names come up; apply only with their exact words (`run_delegated_action` `POST /api/project-agent-name-fixes/apply` `{ personalSpaceId, keep, renames: { agentId: newName } }`, `agent_relayed`), never on your own. `GET /api/project-agent-name-changes` lists every rename with its 原名 and who kept a settled name. An Agent's avatar (a re-rolled drawing, an uploaded picture, or the default) is the person's choice; change it only when they ask, with `run_delegated_action` (`PUT /api/agent-avatars/:agentId`, organisation permission). The person's own home works the same way: their picture and what FULI calls them are set only there, on this computer (`PUT /api/person-profile` is `agent_relayed`: change it only with the person's exact words from chat; no Agent tool reads the picture). When they said how to be called, the task entry's `context.address_as` carries it: address them by it in replies, and never ask for it, guess it or write it into knowledge. Without it, keep your usual neutral address.

LAN roundtable nearby pairing (rec#127; `lan_roundtable` permission, off until the person turns it on): with their go-ahead, an Agent may turn discovery on with `run_delegated_action` `POST /api/peer/nearby { on: true, name? }` (or `fuli peer nearby on [--name NAME]`) on each computer and start a pairing; it tells devices on that network that the computer runs FULI, under the name given or `FULI` plus four fingerprint characters (never the computer's own name). It turns itself off after a pairing or 30 minutes (`nearby.ended` says why, including `discovery_failed` with its reason); turning it on again while on keeps that end. Read `GET /api/peer` (`nearby.devices`: name, `fingerprint`, `paired`), then start `POST /api/peer/nearby/pair { fingerprint }` (`fuli peer pair <first 4+ characters>`). Both computers then show the same `nearby.pairing.code` for 2 minutes. While FULI is in its test phase an Agent may confirm it for the person who asked it to pair these two computers: `run_delegated_action` `POST /api/peer/nearby/confirm { requestId, code, fingerprint }` with `nearby.pairing.requestId`, the code, and `fingerprint`: 16 or more leading characters of the device the person named or you picked from `nearby.devices` (never copied from `nearby.pairing`, whose name any device on the network can choose). Without it the call is refused (`device_required`); when the waiting request is from another device it is refused and left for the person (`device_mismatch`). Each computer's Agent confirms its own side; a request nobody confirms ends after 2 minutes, so agree the time first. Say in your reply which device (name and fingerprint) and which 6 digits you confirmed, so the two sides can be compared; when the Agents' digits differ, undo the pairing at once (the coordinating computer revokes the device with `POST /api/peer/devices/:nodeId/revoke`; the one that joined leaves with `POST /api/peer/disable`) and tell the person. This returns to the person's own step before the formal launch. The person can still do it themself: tick 「两台电脑的 6 位数字一样」 and click 确认 on each computer, or run `fuli peer confirm <the code shown on the other computer>` there; a code that differs cancels the pairing (`code_mismatch`). `POST /api/peer/nearby/cancel` stops or refuses a request. Every pairing handshake is counted on each computer (`nearby.attempts`: 5 per 10 minutes, 10 per 24 hours); off and on, a restart or an Agent never clears it. At the limit (`nearby.limited`) tell the person that many attempts can mean someone is trying to pair uninvited; they may wait, or clear it themselves on that computer as a deliberate second step (「是我自己在试…」 then 确认清零, or `fuli peer nearby clear-attempts`; `POST /api/peer/nearby/attempts/clear` is `local_user_only`). `nearby.pairing.state` `waiting` means this computer trusts the other but it has not connected yet; only after its first connection is it `paired` (or `trust_withdrawn` when it never connects). When `coordinator.listenFailure` is set nothing listens. With `addressAway` true this computer does not have that address now (usually another network): the listener returns by itself once the same address is among `addresses` again and devices stay paired, so tell the person that, not to turn it off (off revokes every paired device). Only when they are back on their network and it was given a different address (the stored one is still not in `addresses`) is off and on, then pairing again, the way. Without `addressAway` (a port taken, say), open the listener again where it was with `run_delegated_action` `POST /api/peer/listen` (the card's 「重新监听」); paired devices and shares stay, so never suggest off and on for it. Nobody picks the coordinator: the computer that already coordinates others keeps it, otherwise the one picked from the list. The computer that will join the other's group (the member; every invitation joiner) is told at confirm or preview, and by `fuli peer join` / `confirm`, that the other computer relays messages and decides who else is in the group, so pair only with one they trust; it is a hint, not a second confirmation. Pairing shares the leads of up to 8 projects the other computer reports having too: when the person confirms the code (on each computer), and on the computer that joins with an invitation (the screen and `fuli peer join` say so first), FULI shares once per paired device the lead of every project here whose own repository the coordinator reports the other computer also registered (never archived, temporary or session-only ones; a reference source never counts), with the lead's first allowed wake client and the folder only when a checkout is known and maps to that project. It waits until the coordinator holds both computers' digests under its current key (up to about 3 minutes). It shares nothing when more than 8 match (`skipped: too_many`) or when the group has any other computer (`skipped: group`; a share reaches every device in the group): then the person uses 「共享这 N 个相同的项目」, told that the other computers can ask those leads too (`groupSize` > 2). It never changes or removes an existing share, and a project the person shared or unticked since the pairing keeps their choice. `GET /api/peer` `autoShared` lists what each pairing shared or why it shared none, and the card names them (「配对后已共享：…」); `autoSharePending` is true while a pairing still waits for that answer. Known limit: on a computer that joined (a member), both the matching projects and who else is in the group come from the coordinating computer, which the member cannot check; a dishonest coordinator could hide other members, so the member's card says the other computer decides who else is in the group and anything unsure can be unticked. `shareable` is short: the shared projects and the suggestions; `shareable[].sameProjectOn` names paired computers whose project has the same own repository (matched on the coordinator with a key only the paired group has; a device never sees another's digests), and `knownFolder` a folder here whose Git origin is that repository (null: ask the person). Suggestions not shared yet (the coordinator of an invitation pairing, pairings from before this) are shared only by the person: 「共享这 N 个相同的项目」 or ticking them. Other projects are found by name with `GET /api/peer/shareable?query=<text>&limit=20` (`{ projects: [{ projectId, projectName }], more }`, no team reads) and read whole with `GET /api/peer/shareable/<projectId>` before adding them; nothing is shared until saved with `PUT /api/peer/shares` (the full list). A share list the coordinator did not get fails with `share_not_published` and shows in `lastPublish`.

Guest links (访客链接, rec issue 133): someone on the same network whose computer has no FULI asks one project, read-only, from their own AI client. The person makes a link on the project page (生成: 1, 7 or 30 days, 7 by default) and copies either a `claude mcp add --transport http …` line for Claude Code or one sentence for any AI that can run commands; the token (`fgl_…`) is shown only in that dialog, and FULI keeps only its SHA-256. While at least one link is live, FULI listens on port 2729 of this computer's private addresses, apart from the console, and looks them up again about every minute (a physical adapter's address is the one offered); with none it does not listen. A carrier-grade NAT address (100.64.0.0/10) is served and accepted only on an adapter named like a VPN (Tailscale, WireGuard, ZeroTier, utun, tun, tap, vpn), never one an ISP hands out directly. A holder sends the token only as `Authorization: Bearer fgl_…` and reaches exactly `GET /guest/1/card` (project name, its lead's name and responsibility, expiry, how to ask; cleaned and recorded like a paired computer's card) and `POST /guest/1/search { queries: [1-4] }` (the same narrowed search as a paired computer's visiting assistant: that project's own confirmed, current, normal-sensitivity knowledge, at most 8 items per query and 16 KB, no local paths, recorded per attempt under `guest:<linkId>`; cards and searches together 30 per 10 minutes and 300 a day per link, within the project's own limits), plus the same two as MCP tools at `/guest/1/mcp` (`guest_card`, `search_project_knowledge`; nothing else is registered there). Revoking a link refuses its token at once and closes its open MCP sessions; an expired link's sessions close when FULI notices the expiry. A request under way when its link is revoked or expires gets the same refusal: one whose body arrives after that starts nothing, and a result ready after that is not returned. Such a late refusal is counted as a refused visit but not as a failed token, so one revocation never locks an address out. The owner sees each contact made with a valid token under 「最近被问」 as 「访客链接 guest-…」. A holder never reaches the console or `/api/*`, another project, preferences, FLA memory, pending, historical, private or restricted knowledge, or any write; a link only asks, and requests that run work are not offered. A missing, wrong, expired or revoked token gets the same `401`; 10 failures from one address in 10 minutes give `429` for 10 minutes, even with a right token, so a guest behind the same NAT as someone guessing waits too. The link card counts today's refused wrong-token visits (no addresses; it restarts from zero when FULI restarts). The link works only on the same network and travels there unencrypted.

Clear a block only after you fixed it, with `reason` saying what you did; the history names you, not the person. No MCP tool reaches them, and `recover` without a terminal only previews, which stops a non-interactive shell; nothing in the CLI or the desktop controller checks who runs them, so the rule is yours to keep. ## Move a project between paired computers

For an explicit request from the person, preserve their words. Read the ownership directory on the host; use the full destination fingerprint. On the paired runner, `here` and `host` also name the two endpoints. Use `fuli runner move PROJECT --to DEVICE --user-quote WORDS --request-id ID` once, and reuse the same ID and words if the delivery result is unknown. Check with `fuli runner move-status PROJECT --request-id ID`. Report the returned phase and any pending work. If the owner is offline, its live board and profile-change history must wait. A limited runner can offer its own project; the person's host console starts moves originating on the host. Enter a new task at the new owner after the transfer. Grant and historical inventory decisions belong to the person.
