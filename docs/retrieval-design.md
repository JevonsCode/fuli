# FULI 怎么找回知识：检索设计报告

2026-11-06。这份报告说明 FULI 如何存知识、如何找回知识，为什么这样选，以及老知识怎么补全。数字来自 `FULI_ALIGNMENT_BENCHMARK.md` 第 8 节用的合成留出集，方法和局限见文末。

## 结论

1. 召回差的主因不是检索算法：20 次没命中里，16 次入口根本没有去搜。
2. 默认不需要任何模型。每次都搜，用中文友好的 BM25 排序，再由当前会话的模型理解语义。
3. 配一个小模型是可选增强，开关不影响知识本身。
4. 老知识用一键补全：先用少量 token 抽样自测，再决定全补、补一部分，还是不补。

## 现在是怎么存的

- 知识以原文存在 Neo4j 图谱里，分词只发生在建索引时。
- 全文索引用 Neo4j 默认分词，中文基本按单字切。
- 现有向量字段是词和字符片段的哈希（`LocalHashEmbedder`），比较的是字面，不是语义。
- 这个哈希方案从 0.2.0 起就在，代码写的理由是不需要模型，也不用联网。没有查到讨论过语义向量后再放弃的记录。

## 我们测到了什么

同一批题，40 个提问，58 条知识，每题取前 3 条，门槛在另一半题上选：

| 方法 | 命中 /32 | 无关题误报 /8 | 每次查询 | 体积 |
|---|---:|---:|---:|---:|
| 现在的入口召回 | 12 | 2 | - | 无 |
| 文件加 grep | 29 | 4 | 0.04 ms | 无 |
| BM25（中文词和二元组） | 31 | 3 | 0.04 ms | 无 |
| `bge-m3` | 32 | 2 | 25 ms | 587 MB |
| `multilingual-e5-small` | 23 | 3 | 6 ms | 135 MB |

除了 `bge-m3`，这批题上的小模型都没有超过 BM25。

本机 Ollama 单独测的结果（直接检索，不走 FULI 入口）：

| 模型 | 命中 /32 | 误报 /8 | 每次查询 | 体积 |
|---|---:|---:|---:|---:|
| `qwen3-embedding:0.6b` | 32 | 1 | 16 ms | 639 MB |
| `embeddinggemma-2:270m` | 28 | 1 | 18 ms | 304 MB |

纯「继续」这种没有主题词的提问，所有方法都是 0/8。带上上一轮摘要后，BM25 到 6/8，`bge-m3` 到 8/8。

## 两种模式

| | 不用模型（默认） | 配小模型 |
|---|---|---|
| 排序 | BM25 | BM25 加向量，倒数排名融合 |
| 语义理解 | 当前会话的模型换说法再搜，搜不到看标题清单 | 向量，再加上左边全部 |
| 安装 | 无 | 本机 Ollama，或在线向量接口 |
| 适合 | 所有人 | 知识多的人 |

两种模式可以随时切换。不用模型的那层一直在，配了模型只是多一层；原文不变，向量是可以丢弃的索引。断开或超时就退回关键词。

### 不写死门槛

不同模型的相似度分数差很多：Qwen 的合适门槛约 0.5，EmbeddingGemma 约 0.77。开放接口不能写死。

所以用这次查询自己的分布判断：分数高于「本次所有条目的平均分加 3 个标准差」才算相关。两个模型都命中 28 到 29 题，误报不超过 2 条，不用按模型校准。这个 3 是在同一批题上选的，还要在更大的数据上验证。

## 老知识怎么补

知识越早存，越可能缺别名和上下文。我们不直接全量处理，而是先花很少的 token 判断值不值。

### 第一步：免费估算

不调用模型。数出条目数、总字数、缺少别名的条目数、疑似重复的条目数，并按字数估算全量补全要多少 token。

### 第二步：抽样自测

抽 20 条，让模型为每条写 2 个「别人可能怎么问」，再用这些问题搜索，看能不能搜回原条目。这一步只花全量的一小部分，而且直接测的是用户关心的事：将来找不找得到。

| 自测命中率 | 建议 |
|---|---|
| 90% 以上 | 不用补 |
| 60% 到 90% | 只补没搜回来的同类条目 |
| 60% 以下 | 全部补 |

这些阈值是初始值，上线后按真实数据调整。

### 第三步：一键补全

页面显示建议和预计花费，用户点一下开始。可以暂停，中断后接着来，每批结果都有记录。

每条知识补两样东西：

- **别名和其他问法**：同义词、中英文说法、它服务的任务。
- **一句上下文**：这条知识属于哪个项目、在什么情况下用。

这两样存进索引字段，不改知识原文，不产生新版本，随时可以丢弃重算。

有模型配置时用配置的模型，没有时打包给当前会话小批处理。

## 借鉴了什么

| 来源 | 思路 | FULI 怎么用 |
|---|---|---|
| Anthropic Contextual Retrieval | 索引前给每段加一句上下文，同时用于向量和 BM25。他们的数据集上，失败率下降 35%（只加向量上下文）、49%（再加 BM25）、67%（再加重排） | 第三步的「一句上下文」，同时进 BM25 和向量 |
| Anthropic Effective context engineering | 按需取，而不是全塞进上下文 | 入口只放少量内容，其余让 Agent 去查 |
| DeepSeek Super-agent（Inline & Spill） | 可能要用的放上下文，其余按需取 | 和上一条同向，FULI 已这样做 |
| DeepSeek Super-agent（链式召回） | 沿任务和会话的 ID 找回历史 | 用上一轮内容补充「继续」这类提问 |

Anthropic 的百分比来自他们自己的数据集，只说明方向，不代表 FULI 的效果。DeepSeek 的设计是实验性的，我们只读了二手报道。

## 还没验证的

- 题是合成的，只有一个项目、58 条知识。知识多了以后，BM25 的精度可能下降，这也是向量的价值所在，但这批题测不出分界点。
- 直接检索的成绩是上限。入口的真实成绩要等改完后端到端重测。
- 抽样自测的阈值和样本量都是设计值。
- 第三步的补全效果还没测过。
- 多轮会话里每次都搜带来的 token 增加，还在测量。
