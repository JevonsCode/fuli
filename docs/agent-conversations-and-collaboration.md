# 对话与协作

Agent ID 是持久身份，Codex、Claude Code 等客户端是工作入口。对话保存在现有
Neo4j Provider 的独立日志中；工作记忆继续保存经过整理的决策和待办。

## 默认行为

| 设置 | 默认 | 含义 |
| --- | --- | --- |
| 压缩阈值 | 64 KB | 未折叠的消息原文超过阈值时，较早的消息折叠进摘要；可配 8–1024 |
| 自动恢复预算 | 4000 UTF-8 字节 | 保守内容上限，不是计费 token；可配 512–16000 |
| 自动恢复 | 摘要 + 最近消息 | 新 chat 恢复同一 Agent、同一项目的最近上下文 |
| 摘要内容 | 最近 12 个任务结果 + 规则摘录 | 用户请求首行，以及用户与 Agent 消息中带决定、更正、未完成或方法标记的原句，附来源角色与序号；最多 6000 字节，省略数量可见 |
| 原始记录保存 | gzip 压缩 | 压缩不删除原文，也不调用模型生成摘要 |

压缩只看对话量，不看时间：闲置多久都不会丢失上下文。每个任务结束时的工作结果写入摘要；
工具输出不自动注入恢复上下文。折叠后的原文仍在数据库，需要细节时用
`read_agent_conversation` 分页补读，不生成虚构摘要。当前任务提示及宿主可见消息各有来源记录。
摘录按固定关键词规则抽取，不理解语义：未带标记的决定会漏掉，带关键词的普通句子可能被误分类；
它不是经核实的工作记忆，原文始终为准。细则见[项目 Agent 记忆](project-agent-memory.md)。
自动恢复和 `resume_agent_conversation` 都把最近一次任务结果单独放在 `context.latest_checkpoint`
（状态 + 结果摘要，从开头保留，超长时标 `truncated`），`context.summary` 标为 `summary_role: historical`，
只含更早的结果和摘录：旧摘录里的 TODO 不代表当前未完成工作，未完成或中断的检查点也不会因此显示为完成。
两者合计仍在恢复预算内（按 JSON 编码字节计，含转义）。交接只携带已保存的文本和引用，不转移本地文件、进程或原生工具状态。
敏感凭据命中检测时整条内容替换为省略标记，因此“原始记录”是已过滤的可见记录。

入口中的偏好保留完整指令，去掉重复证据包装。长期记忆只返回预览；更新前必须
调用 `get_project_agent_memory` 读取完整版本并按 revision 合并。

## 从一个客户端继续到另一个

1. 任务结束返回负责人姓名、主页链接、真实完成状态、`conversation_id` 及保存结果。
2. 在另一个客户端选择同一项目、同一 Agent，取得当前 `taskContextToken`。
3. 调用 `resume_agent_conversation`，传入该 token 和 `conversationId`。
4. 从有预算的上下文继续；需要细节再调用 `read_agent_conversation`。

在已接入 FULI 的客户端、对应项目目录中，可以把提示词写成 `@Alex Morgan 继续上次工作`。
入口只匹配开头的完整姓名或 ID；同名、停用、项目不符或客户端无权限时不会换人兜底。
普通正文或引用里的 @ 不会触发切换。Agent 个人页的对话列表提供“复制接续指令”，
包含稳定 `@{agentId}`、项目 ID 和会话 ID；复制失败时可手动选中。生成的 ID 会编码特殊字符，
改名不影响接续。这是 FULI 的提示词匹配，不表示 Cursor、Codex 的原生 @ 下拉列表已注册此人。

开发者是持久负责人，Jefa/AR 是同级协作角色。只有管理员成员的项目不会把开发任务
隐式记到管理员名下；需要先通过 AR 分配或招聘开发者。显式选中管理员及其本职任务仍可使用。
收尾将实际员工工具返回的协作回执合并展示，例如“Alex 负责实现；Jefa 整理看板”。
没有执行工具或 worker 的配置不能当成协作执行证据；不另起模型来生成这行回执。
派工前分别核对每位成员的客户端与执行器锁，并与任务策略取交集；负责人的推荐平台
不代表协作者也可使用。同一宿主中的原生子 Agent 同样受限制，不匹配时先换合适人选或平台。

接续不会搬运客户端工具状态或文件系统。项目任职、客户端允许列表和个人空间授权
始终生效。来自另一项目的员工仅获得目标项目的任务简报，不自动获得来源项目私有记忆。
历史内容是上下文数据，不能覆盖当前用户指令。

用户的品味、协作性格和判断偏好继续按确认状态和全局/项目/Agent 作用域读取；入口精简
保留完整指令、画像分类和写作品味域。协作职责同时带上 Agent 自己的判断、品味、个性和期望。
工作摘要、AR 配置的性格以及自动推断都不能伪装成人工确认的用户偏好。

## 可选执行框架

Agent 有明确计划时，通过 `record_project_agent_task_activity.executionPlan` 上报当前
步骤快照：`steps` 中每步包含稳定的 `id`、`title`、`status`，可补充 `detail`。
状态支持 `pending`、`in_progress`、`awaiting_review`、`completed`、`blocked`、`skipped`。
后续沿用步骤 ID 并上报完整计划；省略字段表示本次没有更新，`steps: []` 明确撤回计划。
没有计划时不强制生成，也不从模型内部思考推测步骤或百分比。

Agent 主页的当前工作卡及任务执行详情展示最新计划、步骤状态和上报时间。Provider
成功保存任务活动后，通过 SSE 通知页面读取变化任务；同一空间共用一条连接，不轮询。
首次连接及重连同步最新记录，任务结束、详情收起或页面隐藏时取消订阅。断线或读取
失败保留已显示内容并提示更新暂不可用。通知只携带任务 ID，沿用空间读取授权；任务
内容仍由既有接口读取。当前个人 Provider 以单进程运行，通知暂存于该进程，重启后
客户端重新同步数据库。保活心跳不读取任务库。调整保存在原有任务事件中，沿用授权、
版本和幂等检查。
步骤完成是 Agent 上报的进度，不会自动完成任务，也不替代测试或用户验收。

## 采集与失败恢复

Codex 和 Claude Code 的 `UserPromptSubmit`、`Stop` 命令适配器读取宿主提供的当前
JSONL transcript。只支持各适配器明确识别的可见文本、工具调用和结果；不采集隐藏
推理、系统提示，附件二进制及未识别宿主事件不在当前覆盖范围。其他客户端暂保留
任务关联与工作摘要，不宣称已自动同步完整原文。入口只恢复上下文、关联会话，
可见消息统一由转录采集写入，避免同一句提示词被入口和 Hook 重复保存。

首次采集从当前任务起点开始，不导入安装前历史。记录使用稳定事件 ID 去重；游标
与事件在同一事务提交。普通未完成行等待下一次 Hook；数据库失败不推进游标。
超过单条记录限制的内容保存明确省略标记，超长原生行按有界片段推进，后续记录仍可
继续采集。敏感内容、超限记录、附件和未支持的事件不属于“全部原文已保存”。

切换 Agent/项目先验证提示词边界，再把此前记录提交给旧 Agent；每个阶段每次最多
8 页，每页最多 50 条、512 KiB。超过批次会明确阻断本次入口，要求重试，并从已保存
进度继续。完整 EOF 只有在待同步片段未出现未验证用户消息或省略内容时，才可作为
宿主尚未写入新提示词的前置边界；不能仅凭到达 EOF 就认定已找到当前提示词。
若到达 EOF 仍有归属不明的消息，保留宿主原文件；之后找到确定边界时，对这段内容
写省略标记，不把它猜测归入旧 Agent。若宿主始终不写入被阻断的提示词或改变了
其文本，入口会提示新建宿主会话并显式恢复目标 Agent，不能无限重试后猜测放行。

本地仅保留权限为 0600 的原子 guard 文件，包含会话/任务/提示词的不可逆 hash 和
扫描游标，不保存原始提示词、转录路径或另一份对话日志。同会话 Hook 由短生命周期
的 loopback 互斥监听串行保护，不提供任何数据；进程退出后锁自动释放，端口冲突时
安全阻断并提示重试；若持续被其他本地进程占用，可新建宿主会话并恢复目标 Agent。`Stop` 遇到待切换 guard 只续扫或提交已验证边界之前的旧尾部，
不会将当前新提示词写入旧 Agent，也不替用户开启新任务。

正常中断可在同一入口重试继续；`begin_task_context` 成功但边界绑定失败时，只有
保存的新任务 hash 与当前任务一致才能重试绑定。极小窗口内若进程死于任务创建成功、
新 hash 尚未保存之间，将明确要求新建宿主会话：重新选择目标项目和 Agent，使用已
保存的 `conversation_id` 调用 `resume_agent_conversation`，再继续工作。原会话不确定
尾部保留在宿主，不自动导入；不要删除 guard 后强制把旧转录绑定到新 Agent。这些
降级情况需要重试或显式恢复，不宣称无缝接续。

客户端版本必须提供受支持的 Hook 与 transcript 格式；重新接入后需进行真实会话
验收。数据库和解析器测试不等于已验证所有客户端版本。

## 小组长与借调

组长负责拆分、统筹、集成和交付。`plan_agent_collaboration` 返回 `divisionPlan`，
复用现有任职与派工，不额外调用模型生成分工：

| 任务 | 默认工作包 | 开始条件 |
| --- | --- | --- |
| 小改动、只运行已有命令 | 延续一个工作包 | 当前上下文继续 |
| 通常的实质性改动 | 主线实施 + 另一位 FLA 独立验收 | 验收等待稳定产物 |
| 复杂且有明确独立边界 | 主线 + 一个独立工作包 + 独立验收 | 两个执行包可独立推进，验收等待两者产物 |

`taskSize` 默认 `standard`；`small` 只用于低影响小修改，安全敏感或明显改变行为的
工作仍需独立验收。`complex` 本身不制造第三个工作包，还需提供 `independentWork`
的任务类型、无写入冲突或未解决依赖的边界及最多 3 条必要查询。强耦合实现保持在一起，
独立验收可以顺序执行。验收请求不再为自己递归拆出验收者。

调用者传入全部已知 `implementationAgentIds`；验收候选排除这些作者、当前主线负责人
及本轮分配的执行者。实际作者变化后重新规划。先复用本项目合格人员，再走借调和已有
AR 招募流程；不会为填满人数而自动创建身份。每个委派工作包返回派工参数、等待条件
和理由，缺位仍遵守招聘确认政策，借调批准前不执行。

主线复用已有上下文，委派只携带目标、范围、授权产物引用、验收条件与必要查询，
不复制整段会话。派工从每个查询最多 3 个结果起步，缺什么再补什么。模型继续遵循
用户策略、执行器锁和真实可用能力，由 Tonborg 在满足质量要求后考虑成本，不写死
某个厂商或型号。组长将工作包与先后关系上报到已有执行框架，实际 worker、结果和
Token 用量进入任务活动；未报告的用量保持未知，不用估计值冒充节省。

新默认组长采用统筹职责；已有 Agent 的自定义职责不覆盖。普通任务入口与 MCP 指引
都会送达同一分工规则，因此既有组长也适用。FULI 控制面提供计划和记录，由宿主实际
派工，只有真实 worker 记录才表示已经分工执行。

`plan_agent_collaboration` 用职责、能力、任务类型和工作负载推荐成员，优先本项目。
目标组长通过 `request_agent_loan` 发起借调，来源组长在自己的项目上下文中通过
`decide_agent_loan` 确认。数据库创建目标项目中的独立任职；任务完成、失败或取消
自动归还，也支持组长提前结束。固定小组不因临时借调而扩大。

借调成功后仍需 `coordinate_project_agent_task` 明确参与者，再由已授权客户端实际
启动 worker。控制面只提供计划、权限和记录，模型推荐、借调批准都不代表已执行。

项目组长始终是对话负责人，但这不代表适合执行。路由先在固定小组内按能力、任务类型、
负载、同类任务历史和本项目执行连续性选执行者：组长合适就自己做，否则由最合适的成员执行（`project_team_member`），
组长写入任务的协调人并接收汇报。小组无人合格时（`project_team_gap`）走现有 AR 招聘，
遵循“招聘前确认”；合格成员只是当前客户端不可用时任务阻塞，不招聘替代者。
任务入口仅返回 `execution_reason`/`execution_agent_id` 与操作指引，不创建任务、不招聘、不启动 worker。
合格成员只是当前客户端不可用（`agent_unavailable`）时，任务仍由配置的组长协调并接收汇报，
并行计划也不会从小组外补人；显式指定的协调人优先。

`plan_agent_collaboration` 按与 Provider 相同的有效能力匹配专家：任务分配上的能力非空时取代档案能力，
而不是合并。结果排除当前客户端不可用、分配未激活、来源项目组长本人（组长不可借调）的 Agent，
只返回公开的角色与分配信息。每个候选附 `nextSteps`：`message_agent` 只是圆桌咨询（只读、advisory），
跨项目执行需目标组长 `request_agent_loan`、来源组长 `decide_agent_loan` 批准，再用
`coordinate_project_agent_task` 由授权运行时执行，结果回报组长。没有合格专家时返回 `recruitment`，
指向现有 `coordinate_project_agent_task`（`staffingIntent: new_durable`）与同一 `idempotencyKey`，
遵循“招聘前确认”；发现、消息与招聘都不算已执行的工作。

## 模型和验证

自适应策略按简单、普通、复杂任务映射到 fast、balanced、deep。显式用户策略、
模型与执行器锁保留。注册执行器的预检模型可提供 `capabilityTier`（1–3）和
`costRank`（非负相对成本）；等级是本系统的配置约定，不冒充模型厂商能力评测。
选择通过授权、预检、工作区权限和健康检查的模型，在满足能力要求后选择成本较低者。
缺少能力证据时质量门禁阻塞，不凭模型名称猜测。

验证先报告实际 executor run，绑定 `artifactRevision`，再调用
`record_agent_verification`，提供相同 run、模型、版本和测试证据引用。同一 run
不能重复计次。连续两次同档验证失败提高能力下限；最高档连续失败需人工处理。
旧版本验证不能放行新版本。新协调任务只有当前产物验证通过后才能标为完成；
历史任务保持兼容。验证证据由宿主报告，Provider 不伪装成自己执行了测试。
后来提交的产物验证失败会关闭任务完成门禁；旧版本的通过证据仍可查询，但不能
静默用旧结果放行当前任务。修复后的目标版本需重新验证通过。

验证客户端优先应用用户已有项目/全局规则。没有规则且有多个已授权候选时，规划
返回一次可选选择及 15 秒期限，宿主可询问用户：仅本项目还是全部项目。未回答时
只使用当前任务默认项，不写入永久偏好、不扩大权限。这里返回的是宿主交互协议，
不是服务器后台弹窗或自动倒计时执行器。未注册软件不能因被检测到就自动获得权限。

## 界面

默认突出负责人、状态和当前工作；对话按需展开。执行器、路由、学习和技术明细
收在高级区域。记忆设置提供压缩阈值、恢复预算及采集开关，读取失败可重试。

## 设计参考与验证

- [LangGraph stores](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/stores.mdx)：区分会话状态与长期记忆。
- [Letta Agent File](https://github.com/letta-ai/agent-file)：分开历史记录与送入模型的上下文。
- [OpenHands event store](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/conversation/event_store.py)：事件日志与恢复。

当前实现的压缩阈值、字节预算、能力档位、两次失败和 15 秒期限是产品配置选择，
不是以上项目的默认配置。数据库集成测试只使用一次性本机数据库和合成数据。
