# 复利 README 重写设计

## 目标

根 README 同时服务普通用户和开源开发者。普通用户应在前半部分理解复利解决的问题、核心工作流和 Agent 接入方式；开发者应在后半部分找到准确的架构、运行命令、模块边界和项目状态。

## 写作原则

1. 产品定位先于实现细节。
2. 先给一条可运行的最短路径，再给完整参考。
3. 已实现、正在建设和终局设计必须明确分开。
4. 不把未实现的安装命令写成快速开始。
5. 不把 Web 描述成主要输入入口；知识主要通过 Agent 和自动观察自然沉淀。
6. 强调人的最终判断权，以及个人数据不会自动进入公共空间。
7. 使用中文为主，保留必要的技术名词、命令和协议名称。

## 信息结构

1. 项目名称与一句话定位
2. 复利要解决的问题
3. 核心理念
4. 一个真实工作流
5. 当前实现状态
6. 五分钟运行
7. Codex 与 Claude Code 接入
8. 系统架构图
9. 个人空间、工作空间与数据流
10. 记忆演化、来源和人的判断权
11. Web、CLI、MCP 使用参考
12. 代码结构与本地开发
13. 尚未实现的部分与 Roadmap
14. 设计文档、许可证

## 内容边界

README 保留用户实际需要的命令和 MCP 配置示例，但不展开 Workspace Protocol 的字段级约束、迁移实现细节或测试矩阵。这些内容通过链接指向正式设计文档。

`fuli setup`、`fuli deploy`、远程 Workspace Provider、OIDC、OpenFGA、PostgreSQL 和跨端同步必须标为规划中。当前可运行入口只使用仓库已经支持的 Node.js、Web、CLI 和 MCP 命令。

## 验收标准

- 新读者能在前三屏回答“复利是什么、为什么不是笔记软件、现在能做什么”。
- 快速开始中的每条命令都能在当前仓库执行。
- README 中不存在已经失效的旧 Web 入口描述。
- 架构图准确区分本地已实现能力和远程规划能力。
- MCP 工具、环境变量和默认数据库路径与代码一致。
- 全文没有占位符或模糊的完成状态。
