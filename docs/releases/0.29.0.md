# FULI 0.29.0

## 未发布 · Unreleased

FULI 自己开的项目（以前叫「会话项目 / Conversation project」「临时会话」「临时任务」）不再存一个写死的名字，在控制台里都叫「临时项目 #编号」，界面是中文就显示中文，英文就显示英文。你起过名的项目不动。它们的负责人显示成「临时项目的助手」。[临时项目](https://github.com/JevonsCode/fuli/pull/1074)

FLA 的名字在个人空间里不再重复：新雇的、改名的都不会和别人同名，两个同时抢一个名字也只有一个成功。名字被占用时，会说是谁在用、在哪个项目，并给几个可用的名字。[FLA 名字唯一](https://github.com/JevonsCode/fuli/pull/1083)

以前就重名的 FLA，升级后什么都不用点，FULI 照常可用，名字也先不动。想整理时，在 FLA 页点「查看并处理」：每个重名会列出谁保留、谁改成什么、为什么；可以换人保留，也可以不改某一位，点一次「全部处理」就改完。改掉的名字记在「改名记录」里，30 天内用原名 `#FLA` 也找得到他；这 30 天里别的 FLA 也不能用这个原名。在两位都不在的目录里用原名点名，会直接点到现在叫这个名字的那位，并说一句另一位现在叫什么。这个版本之前人做的改名没有留改名记录：如果当时选的是系统建议的名字，现在会被当成系统起的，排谁保留名字时不算「你起的名字」。

**FLA 页先说它现在在做什么。** 名字下面一行就是「现在」：正在做哪件事、做到哪一步、记下的进度（比如 5/8，没有计划就不画进度条）、在哪个客户端里做、最近一次进展是多久前（比如「最近进展 3 天前」，做了多久放在悬停提示里）；没活时照实说「现在没活」并给出最近做完的一件；有事等你拍板时直接给「去处理」。任务在记录里还在进行，就照实说「正在做」，旁边写明最近一次进展的时间，FULI 不替你断定它停了；圆点只在半小时内有进展时闪动，否则是静止的灰点；同时有别的事等你拍板、起步包还没选、经验等你定留不留时，「现在」下面各给一行，点一下就到。以前占首屏的起步包收到页面最下面，选好后收起；职责完整显示一次；按天的活动日历仍在，放在「在哪干的活」下面，翻到那里才读取；「复制 #FLA」换成一个「交给它一件事」按钮，点一下就在 Codex、Claude Code 等客户端里带着开场话新开对话，都打不开时才复制，并说明原因和去哪设置。[FLA 页](https://github.com/JevonsCode/fuli/pull/1067)

**数据格式：图谱从 22 升到 25，其中一步要你确认一次。** 升级后，如果图谱里有这些自动起名的项目，FULI 会先把图谱设成只读，直到你确认：新的知识存不进去，项目和 FLA 也改不了，新任务记不下来。顶部会提示「数据格式更新等你确认」，点「去处理」到 设置 › 系统 › 数据格式，页面会写明要改什么和改多少个项目，点一次「应用这些迁移」就处理完全部。这一步只去掉 FULI 自己起的名字，并把这些项目标成临时项目；任务、知识和 FLA 都不动。确认后可以在同一页撤销：之后新建的临时项目会补回旧的固定名字，撤销结果会写明补了几个，撤销后旧版 FULI 能照常读取。但确认后改名或归档过这次改动的项目，撤销会被拒绝；那时只能用确认前留的图谱备份整库恢复，之后的改动都会丢。所以数据格式页在「应用这些迁移」前面有一个「先备份图谱」按钮：点一下，FULI 暂停一会儿，把整个图谱备份到数据文件夹的 `backups/graph/before-format-23-<时间>`，完成后自动回来，页面写明备份在哪、多大（磁盘放不下时先说明，不会停 FULI）。撤销被拒绝时，同一页会给出「用这份备份恢复…」：确认之后的改动都会丢，FULI 停下、整库导回、再启动，恢复前的图谱另存一份。确认前没有备份时，页面会如实说明。旧版本的 FULI 打不开 23、24、25 版的图谱：要退回旧版本，先在数据格式页撤销这一步，图谱回到 22。没有这类项目的图谱会自动升到 23，不用确认。确认（或自动升到 23）之后，FULI 自己接着升到 24：这一步只给 FLA 名字加一条唯一规则，不改任何记录，不用确认；它不单独出现在撤销里，撤销 23 时这条规则留在图谱里，旧版 FULI 照常读写，不受影响。接着自动升到 25：这一步只登记一组新字段，供以后在这台电脑上保留另一台电脑数据的只读副本时，给副本里的每条记录标上它来自哪台电脑、属于哪个范围、何时同步；不改任何记录，不用确认，这个版本还不会写这些字段。图谱到了 25，24 版的 FULI 会拒绝打开它，不会把副本当成自己的数据去改。

**桌面窗口：导入没做完时点按钮就能回去。** 容器模式和 Windows 原生模式下，整库导入被打断后 FULI 不会启动；以前窗口只给命令让你复制到终端，现在主按钮是「导回到导入前并启动」（没有副本时是「重新运行那次导入并启动」）：先说明用哪一份副本、哪些图谱会回到导入前，你确认后导回并启动。导回走不通时，确认框里有「放弃这次导入…」：可能只写了一半的图谱挪开（不删除），做完告诉你挪到哪里、怎么搬回来。macOS 原生模式下如果也留着这种导入记录（比如数据目录是从 Windows 拷来的），先按维护锁恢复，之后同样给这两个按钮。macOS 原生模式的「恢复并启动」从副本导回时，如果是 FULI 之前没关掉的图数据库占着库，确认按钮变成「结束它并重试导回」：先结束这个进程（只结束认出是这份数据的），再接着导回；认不出的进程不动，只写明进程号；只有本数据目录受管的 Neo4j 进程才算认得出，在那个目录里查看日志的命令或终端不算。导回或放弃导入还在后台进行时，窗口会说明，不会再启动第二次导入。数据库维护锁里记下的占用进程多了一个可选字段 `own`（是否认出是本数据目录的 Neo4j），旧版本留下的锁没有这个字段时按「认不出」处理。

跟随另一台电脑的 FULI（从机）现在也会给自己准备一套本机数据库：更新后第一次启动时在后台装好、试着启动一次、再停掉，没有本机项目时不常驻；磁盘不够 3 GB 就不装，并说还差多少。状态带、本机页面、`fuli status` 和 `fuli routes list` 会说它准备到哪一步，并写明每个项目归哪台电脑（本机 / 主机）。`fuli routes follow` 以前核对「本机有没有这个项目」时问错了地方（问到了主机），现在问本机自己的数据库。

新项目可以在「本机」页（`/local`）点「放在这台电脑」，也可以请 AI 使用 `keep_project_on_this_computer`，或在终端执行 `fuli routes local` 并指定文件夹。项目放好后，主机离线也能工作。招聘送出前会再确认；如果主机已收到请求，撤回时它已经建好的 FLA 会留在主机名册。离开主机后，请在这台电脑上取消仍在等待的招聘，再重新发起。路由库升级到 v2 后，旧 beta 无法读取。整图备份只能恢复到原电脑。

从机给自己建的本机图谱，现在用主机的个人空间编号，这样以后才能把主机的全局习惯和 FLA 名册原样复制过来。主机不在线或还是旧版本时，只装好数据库、先不建图谱，等连上新版主机后自动补上，不用你做什么；之前这台电脑自己建过的空图谱会挪到 `native-runtime/recovered/` 里留着，不删除。这台电脑原来就有自己的 FULI 数据时什么都不动，状态带和本机页面会说清楚：空间和主机不同，所以现在不能在这台电脑上拥有本机项目，项目照常在主机上做。

从机现在会把主机的全局习惯和 FLA 名册复制一份到本机图谱里，只读、不改，记下上次同步的时间。第一次在本机图谱建好时顺手做；之前已经准备好的从机、或者第一次没同步成功的，会在这台电脑的控制台启动、且主机在线时补上：为此启动一次本机数据库，同步完就停掉。主机不在线、或者主机还是会说同样的拒绝时，不会启动。FULI 升级后也会这样启动一次，让本机图谱格式跟上并核对副本。之后只在本机数据库本来就开着时，每 10 分钟问一次主机有没有变化，变了才取，每小时还会整份核对一次，本机图谱被别的途径改过也会改回主机的内容。状态带、本机页面和 `fuli status` 会说副本上次核对的时间，以及同步不了的原因：主机不在线、主机还是旧版本、两台电脑的 FULI 版本不一致、或者被拒绝（写明哪边拒绝、为什么）；所有调用照旧去主机。从机上的 `fuli graph import/export`、`fuli graph runtime update/rollback/recover`、`fuli graph migrate`、`fuli migrate reconcile-knowledge` 和桌面应用的恢复操作现在会直接说明这台电脑的图谱由 FULI 管理、什么都没改，并指向主机或 `fuli runner leave`，不会再把本机数据库当普通 FULI 启动；`fuli migrate` 的其余命令照常处理从机自己的存储，只是不包含图谱，并说明这一点。为补副本启动过本机数据库、导入却没完成（超时或中断）时，同一份副本、同样的版本下不会再为它启动，直到主机内容或版本变了，或在本机页面按「重新准备」。

没有 hook 的客户端（比如 Claude Desktop、Cursor）以前每问一句都把你的全部习惯原文再拿一遍，问一句和习惯无关的话也带上 68 条。现在和 Claude Code 一样：硬性规则一定带全文，其余按相关程度在额度内带一部分，剩下的写明还有几条、随时可读；同一个对话里再问，习惯没变就只重复硬性规则。回执那句也就成了「直接带上 X 条，另外 Y 条随时可读」。

Codex 只完整保留每轮开头约 1 万字节的 FULI 内容，多出来的从中间截掉：以前一个习惯多的任务每轮都整段重发 6 万多字节，Codex 看得到的只是头尾，被截掉的习惯（往往包括硬性规则）它不知道。现在 Codex 的入口和 Claude Code 一样控制在这个额度里：放得下的硬性规则带全文，放不下的写明「还有硬性规则没列出，先读再动手」并给出读取方式；同一个对话里习惯没变就只发变化。

只在某种情况下才适用的习惯，这次任务明显不是那种情况时就不带全文了，硬性规则也一样：入口里只写一行「这条讲什么、什么时候适用」，真遇到那种情况，AI 按名字读全文再动手。判断不了的（比如只说了「继续」）照旧带上。回执会说「另外 Y 条随时可读（其中 Z 条这次用不上）」。硬性规则的那一行还会带上规则正文的第一句，让 AI 看得出它讲什么。只有你明确说过「这条只在某种情况下适用」时才写它的「适用条件」（appliesWhen）；「仅限内部使用」这类写法和「总是」「所有任务」不算条件，照常带全文。

没写「只在什么时候适用」的习惯，哪怕明显只讲某一类事，也会每次都带全文。现在偏好页会数出这样的习惯有几条（其中几条是硬性规则），点一下交给你的 AI：它给每条拟一句「只在……时适用」，一次列给你勾，你勾了的才写上，可以改写或跳过；改动留在历史里。

 “会话项目 / Conversation project”, “Temporary session”, “Temporary task”) no longer store a fixed name. The console calls them “Temporary project #number” in its own language, and their leads read “Temporary project assistant”. Projects you named stay as they are.

FLA names no longer repeat in a personal space: a new hire or a rename never takes another FLA's name, and of two writes racing for one name only one succeeds. A taken name says who has it and where, and offers free names.

FLAs that already shared a name need nothing after the upgrade: FULI keeps working and nobody is renamed. When you want to tidy up, Review on the FLAs page lists each shared name, who keeps it, what each other FLA becomes and why. Let another keep it or leave a rename out, then one Rename all does the rest. Old names stay in the rename history, and for 30 days `#FLA` still finds an FLA by its old name and no other FLA may take it. Outside both FLAs' projects, the old name reaches the FLA called that now, and the entry says what the other is called. Renames made before this version left no rename history: a name a person picked from FULI's suggestions then now counts as one FULI gave, not one you gave, when deciding who keeps a shared name.

**The FLA page says first what the assistant is doing.** The line under its name is now “Now”: the task it is on, the step, the recorded count (5/8, say; no bar without a plan), the clients it runs in, and when it last made progress (“Last progress 3 days ago”; how long it has run is on hover). With nothing on its hands it says so and names the last task it finished; a decision waiting on you comes with “Take a look”. A task the records say is running reads “Working on” with the time of its last progress beside it; FULI does not decide for you that it stopped. The dot pulses only after progress in the last half hour, and otherwise stays a still grey. When another task needs your call, starter kit picks are still owed or experiences wait to be kept or dropped, a short line under “Now” says so and takes you there. The starter kit that filled the first screen moved to the bottom and folds once answered, the responsibility shows once in full, the daily activity calendar stays, below “Where it worked”, and is read only when you scroll to it, and “Copy #FLA” became one “Give it something to do” button: one click opens a new conversation in Codex, Claude Code or another client with the opening message in it; only when none can does it copy, saying why and where to set that up.

**Data format: the graph moves from 22 to 25, and one step asks you to confirm once.** If the graph holds such projects, FULI keeps it read-only after the upgrade until you confirm: new knowledge is not saved, projects and FLAs cannot be edited, and new tasks are not recorded. A banner says a data format update waits for you; 去处理 opens Settings › System › Data format, which says what changes and for how many projects. One “Apply these migrations” handles them all. It only removes the names FULI generated and marks those projects temporary; tasks, knowledge and FLAs are untouched. You can undo it on the same page: temporary projects created since get back the old fixed name, the result says how many, and an older FULI then reads the graph. If you rename or archive one of the changed projects after confirming, the undo is refused; then only a graph backup taken before you confirmed brings the old version back, and every change since is lost. So the data format page has a “Back up the graph first” button before “Apply these migrations”: one click pauses FULI for a while, backs the whole graph up to `backups/graph/before-format-23-<time>` in the data folder and brings FULI back, and the page says where the backup is and how big (when the disk cannot hold it, it says so first and does not stop FULI). If an undo is refused, the same page offers “Restore from this backup…”: once you confirm that every later change is lost, FULI stops, imports the backup whole and starts again, keeping a copy of the graph as it was. Without a backup from before you confirmed, the page says so. An older FULI cannot open a version-23, 24 or 25 graph: before going back, undo the step on the data format page, which takes the graph back to 22. A graph without such projects moves to 23 by itself. Once 23 is in place, FULI moves on to 24 by itself: that step only adds the rule that keeps FLA names unique, changes no record and asks nothing. It is not undone on its own: undoing 23 leaves the rule in the graph, and an older FULI reads and writes as before. FULI then moves on to 25 by itself: it only registers new fields that will mark each record of a read-only copy of another computer's data with the computer it came from, its scope and when it was synced. It changes no record, asks nothing, and this version does not write those fields yet. A FULI of version 24 refuses a graph at 25, so it never edits a copy as if it were its own.

**Desktop window: an unfinished import goes back by a button.** In container mode and native mode on Windows, FULI does not start after a whole-graph import was interrupted; the window used to give you commands to copy into a terminal. Its main button is now “Go back and start” (“Import again and start” when no copy holds the graph): it says which copy it uses and which graphs go back, and after you confirm brings them back and starts. If that does not work, “Abandon the import…” sits in the same confirmation: the graph that may be half written moves aside (not deleted), and the window then says where it went and how to move it back. If such an import record is left in macOS native mode too (a data directory copied from Windows, say), the maintenance lock is recovered first, then the same two buttons appear. In macOS native mode, when “Recover and start” could not bring the copy back because a graph database FULI did not stop held the store, the confirm button reads “End it and retry”: it ends that process (only one recognised as this data's) and goes on; a process FULI does not recognise is left alone and named by its PID. Only this data's managed Neo4j counts as recognised; a command or terminal reading logs in that folder does not. While a way back or giving up still runs in the background, the window says so and never starts a second import. The processes recorded in the database maintenance lock carry a new optional field, `own` (whether FULI recognised it as this data's Neo4j); a lock an older version left without it is treated as not recognised.

A computer that follows another FULI now prepares a database of its own too: after the update, its first start installs it in the background, starts it once to check it, and stops it again, so it does not sit in memory when there are no local projects; with less than 3 GB free it installs nothing and says how much is missing. The state band, this computer's own page, `fuli status` and `fuli routes list` say how far it got and which computer each project belongs to. `fuli routes follow` used to check the host instead of this computer when asking whether this computer already has a project; it now asks this computer's own database.

To keep a new project here, use “Keep on this computer” on `/local`, ask your AI to use `keep_project_on_this_computer`, or run `fuli routes local` with the folder. The project can then work offline. An unsent recruitment is checked again before delivery. If the host already received it, the FLA it created can remain on its roster. After leaving the host, cancel outstanding recruitments and request them again on this computer. Earlier betas cannot read the upgraded v2 route store. Full graph backups restore only to the computer that created them.

A follower's own graph now uses the host's personal space ID, so the host's global habits and FLA roster can later be copied into it exactly. While the host is away or runs an earlier FULI, the database is only installed and no graph is made yet; it is made by itself once a new enough host answers, with nothing to do. An empty graph this computer made earlier under its own ID is moved to `native-runtime/recovered/`, never deleted. A computer that already has FULI data of its own is left alone, and the state band and this computer's page say so: its space differs from the host's, so it cannot own a project here for now, and projects go on on the host.

A follower now keeps a read-only copy of the host's global habits and FLA roster in its own graph, never edited, with the time it was last synced. The first copy comes when its graph is made; a follower prepared earlier, or one whose first sync failed, gets it once its console runs and the host answers: the database is started once for it and stopped again, and not at all while the host is away or would only refuse again the same way. A FULI update starts it once the same way, to bring the graph format up to date and check the copy. After that, only while its own database runs anyway, it asks the host every 10 minutes whether anything changed and fetches the copy only then; once an hour it imports the whole copy anyway, so a graph changed some other way is brought back to the host's. The state band, this computer's page and `fuli status` say when the copy was last checked, or why it could not be: the host is away, the host runs an earlier FULI, the two computers run different FULI versions, or it was refused (by which side and why). Every call still goes to the host. On a follower, `fuli graph import/export`, `fuli graph runtime update/rollback/recover`, `fuli graph migrate`, `fuli migrate reconcile-knowledge` and the desktop app's recovery actions now say that FULI manages this graph and nothing was changed, pointing at the host or `fuli runner leave`, instead of starting the database as an ordinary FULI's; the other `fuli migrate` commands work on the follower's own stores as before, leave the graph out and say so. When the database was started for the copy and its import did not finish (timed out or interrupted), it is not started for the same copy at the same versions again until the host's content or a version changes, or 「重新准备」 is pressed on this computer's page.

Clients without a prompt hook (Claude Desktop, Cursor) used to fetch every one of your habits in full on every message, 68 of them for a question that had nothing to do with habits. Now they get what Claude Code gets: hard rules always in full, the most relevant others within a budget, and a one-line summary of each of the rest, readable any time; a later message in the same conversation repeats only the hard rules while nothing changed. The receipt then says how many came directly and how many are there to read.

Codex keeps only about the first 10,000 bytes of what FULI hands it each turn and cuts the rest out of the middle. A task with many habits used to resend its whole 64 KB entry every turn while Codex saw only its head and tail, so the habits in the cut, hard rules often among them, were silently lost. Codex's entry now stays within that limit as Claude Code's does: the hard rules that fit come in full, any that do not are named as missing with how to read them before acting, and a later turn in the same conversation sends only what changed.

A habit that applies only in some case is no longer carried in full when the task is clearly not that case, hard rules included: the entry gives one line saying what case it is for, and the AI reads it by name when the task turns out to be that case. When FULI cannot tell (a message that only says "go on"), it carries the habit as before. The receipt says how many of the readable ones were not needed this time. A hard rule's line also gives the first sentence of what it says, so the AI can tell what it is about. Give a habit an appliesWhen only when you said it applies only in some case; "Only for internal use" and "always" or "all tasks" are not cases, and such habits are carried in full as before.

A habit that never says when it applies is carried in full on every task, even one plainly about a single kind of work. The preferences page now counts such habits (and how many are hard rules) and hands them to your AI in one click: it drafts a short "only when …" for each and lists them once for you to tick, reword or skip, and writes only what you ticked; each change stays in the habit's history.

### 改了什么

- **运行机（Beta）**：在主机上运行 `fuli runner invite`，把打印出的一行在另一台电脑上运行（`fuli runner join …`，10 分钟内有效，只能用一次）。两台电脑互相固定对方的证书（双向 TLS 1.3），运行机上的 Codex、Cursor 和其他 MCP 客户端随即按 `fuli setup` 的方式接好，它们的 FULI 工具都由主机回答。知识、习惯、FLA 和记忆只存在主机上。
- **目录不同也认得项目**：运行机把所在目录的仓库信息（来源地址，不带任何凭据）告诉主机，主机按本机同样的规则认项目、登记新仓库，不读运行机的硬盘。
- **主机暂时连不上**：任务进入用这个目录上次的偏好（标明是离线结果），`checkpoint_task_knowledge` 先排队，其他只读工具给上次的结果，别的操作明确说需要主机。连上后按顺序补交，主机记住每一条，重复送达只算一次。`fuli runner status` 查看，`fuli runner sync` 立即补交。
- **地址变了也找得回来**：主机跟着自己的局域网地址变化监听，并用 mDNS 公布证书指纹；运行机先试上次的地址，再按指纹找。
- **管理**：主机上 `fuli runner list` 列出运行机和最后在哪里见到，`fuli runner revoke` 立即收回访问。邀请运行机只能由你本人在主机上做。

### 这一版的限制

- 两台电脑要能直接连通（同一网络或一根线），不经过任何中继。
- 运行机上不跑生命周期 hook，客户端靠 FULI 的 MCP 工具自己进入任务。

## In English

### New

- **Runners (Beta).** On the host run `fuli runner invite`, then run the printed line on the other computer (`fuli runner join …`, valid once, for 10 minutes). The two computers pin each other's certificates (mutual TLS 1.3); the runner's Codex, Cursor and other MCP clients are set up as `fuli setup` would, and their FULI tools are answered by the host. Knowledge, preferences, FLAs and memory stay on the host only.
- **Projects match whatever the folder is called.** A runner tells the host its folder's repository facts (the origin address, never a credential); the host matches and registers projects by its own rules without reading the runner's disk.
- **While the host is away.** Task entry returns the folder's last preferences, marked offline; `checkpoint_task_knowledge` queues; other read-only tools return their last answer; anything else says it needs the host. The queue is delivered in order once the host answers; the host remembers every entry, so one delivered twice counts once. `fuli runner status` shows it, `fuli runner sync` delivers now.
- **Found again after an address change.** The host follows its LAN addresses and announces its certificate fingerprint over mDNS; a runner tries the last address, then looks the fingerprint up.
- **Managing runners.** `fuli runner list` on the host shows each runner and where it was last seen; `fuli runner revoke` ends its access at once. Only you can invite a runner, on the host.

### Limits of this beta

- Both computers must reach each other directly (one network or a cable); nothing is relayed.
- Lifecycle hooks do not run on a runner; its clients enter tasks through FULI's MCP tools.
