# 召回成功率基线

`npm run measure:recall-rate`，2026-11-24 重量（`origin/main` 195c9812）。虚构世界 37 条知识
（其中 5 条没有手写检索词）、2 个项目、1 个个人空间；不连 Neo4j、不用嵌入模型、不调任何模型，
本机约 2 秒。量法和它看不到的东西见 `acceptance/recall-rate/README.md`。

## 这把尺子能说明什么

- **竞争很少。** 按需检索每个查询平均有 14.1 条参与打分（关系先按「和查询至少共享一个词」筛过，
  实体是范围内全部），其中 4.1 条打出分；每次调用平均送出 2–2.5 条。入口每个任务送出 1.8 条。
- **题是照着答案写的。** 原有 21 次调用里，标准答案大多手写了和查询逐字对得上的检索词；
  把检索词全部去掉，常规题的标准答案送达从 23/23 降到 21/23（见下文「检索词贡献了多少」）。
- **镜像不是完整的检索。** Graphiti 的混合检索（分词、按意思找的候选、它自己的次序）、向量与
  RRF 融合、鉴权、Cypher 侧过滤、标签重排都不在里面；候选池是按「共享一个词」近似的。
- 所以「满分」只说明：真代码（入口的查询生成、过滤、预算；搜索页的预算；Provider 的打分函数）
  在这个小世界上和写好的答案一致，以及一处改动让这些数字往哪边走。它**说明不了真实库里的召回率**。

## 逐项：去掉 null 字段带来了什么

只改 `search_current_project_knowledge` 和 `search_knowledge_graph` 交给 Agent 的页面：一条结果
不再带约 15 个值为 null 的字段（rec#111）。打分、排序、数据格式都不变。

| C（按需检索） | main | 去掉 null 字段 |
|---|---:|---:|
| 标准答案送达（常规题 / 全部） | 22/23 · 30/39 | **23/23 · 33/39** |
| 被预算挤掉的标准答案 | 5 | **2** |
| 被预算截断的调用 | 14/37 | 13/37 |
| 每次调用送出条目 | 2.00 | 2.49 |
| 每次体积 | 4635 B | 4572 B |
| 整体精确率（送出条目里标准答案的比例） | 0.405 | **0.359** |

- 每条结果变小，同一页装下的条目变多：送达和「被预算挤掉」都变好，主要在「只靠项目名」那类
  （送达 1/5 → 3/5）和 `sc-broad-first-zh`。
- 代价照实写：多装进来的不全是标准答案，偏题也跟着变多，整体精确率从 0.405 降到 0.359（常规题
  0.512 → 0.469）。每次体积只降了约 1%，因为省下的字节被多装的条目又用掉了；省下的是每条结果里
  null 字段那部分（rec#111 估计约占一条的五分之一）。

## 新题：四类难例（已知缺口）

每类单独统计，也计入总表。C 列是「标准答案送达 / 前 5 命中」，精确率 = 送出条目里标准答案的比例
（口径和 B 一样严，不是标准答案都算偏题）。

| 类别 | 题数 | main | 本分支 |
|---|---:|---|---|
| 近义不同词（上线↔发布、值守↔值班） | C 4 · B 1 | C 0/4 · 0/4；B 1/1 | 同 main |
| 只靠项目名共享 | C 5 · B 1 | C 1/5 · 3/5，MRR 0.222，0.067；B 0/1 | C **3/5** · 3/5，MRR 0.222，0.120；B 0/1 |
| 两个项目里同名 | C 4 | C 4/4，MRR 1，0.364 | C 4/4，MRR 1，0.308 |
| 没有手写检索词 | C 3 · B 1 | C 3/3，0.6；B 1/1 | 同 main |

- **近义不同词 0/4**：没有向量的镜像里本来就召回不了——没有共享的词，也没有能接上的检索词。要靠
  向量（或记录时写对检索词）补，不在这里硬编同义词表。
- **只靠项目名**：查询和答案只共享项目名，于是这个项目的每条知识都同样算命中，答案排第 3–9 名；
  多送的两题是靠页面变小装进来的，排序本身没变好。
- **同名跨项目**：四题的答案都排第 1，但每题前 5 都带着另一个项目的同名条目。`sc-same-named-other`
  （在潮池账本里点名问「灯笼鱼官网 发布流程」）答案排第 1。
- **没有检索词**：三题都在第 1 名，入口那题也召回了。

## 试过、没有采用

两处打分改动在这个 PR 里实现过、量过，评审逐项撤掉重跑后回退到 main 的行为。

**① 关系的查询词按区分度加权**（实体那条路从 rec#111 起已经这样做）。只命中常见词（比如项目名）的
关系保留加权前分数的 5%，排在所有靠区分词命中的条目后面。
- 量到的收益：只有 `sc-principle-zh` 从第 3 名升到第 2 名（常规题 MRR 0.877 → 0.885），「只靠项目名」
  前 5 命中 3 → 4。最早的版本把只命中常见词的关系判 0 分，B 精确率 0.448 → 0.619，但「只靠项目名」
  5 题全丢，所以改成只排序。
- 没采用的原因：`sc-same-named-other` 里，项目名被压轻后，当前项目那条（题目标明不该出现的
  `lg-release-runbook`）排到第 1、正确答案掉到第 2。AI 通常先读第一条，真实使用里就是拿到错项目的
  答案。有向量时 RRF 只看名次，这个加权的实际效果也没量过。
- 想再做先要解决：点名的项目名不能被当成常见词压轻；然后在 Neo4j 上带向量评估，而不只在这个镜像上。

**② 跨查询按「占本查询第一名的比例」排序**（同一轮里谁更接近自己查询的第一名谁先上）。
- 量到的收益：基准上零（撤掉前后所有数字一致）。
- 没采用的原因：比例对分数的分布形状并不中立。有向量的查询是 RRF 分数（K=60，第 1 名约 1/61、
  第 5 名约 1/65，比例都在 0.94 以上），纯词法查询第 5 名的比例可能只有 0.3，所以一次调用里有向量
  的查询从第二轮起几乎永远排前面。翻页游标也随分数次序变化，两页之间分数一变就更容易失效。
- 想再做先要解决：一个和分布形状无关、跨查询可比的分数（比如 Provider 给出的名次或校准过的置信度）。

**排序本身在聚焦查询上是好的**（MRR 0.908，标准答案全部进了前 5）。问题全在两处：

1. **查询里只要带项目名，这个项目的东西就全都算命中。**
   `sc-named-project-zh`（查询「潮池账本 发布流程」「潮池账本 打 tag 命令」）排出 **22 条**，
   前 5 条里有 3 条是明确标注的干扰项，最后只送出 3 条。
   `sc-principle-zh`（查询「潮池账本 产品原则」等 4 句）排出 16 条，第 2 条是无关的
   「界面文案中英双语」偏好——和 rec#111 11-10 表格里那条 1.85 分的宣传偏好是同一回事。

   原因确定了：`_relevance` 里按「这个词能分辨多少候选」加权的那套（`_term_weights`、
   `_too_common`，注释里直接写着「rec#111」）**只接在实体这条路上，关系这条路没接**。
   `_edge_relevance` 调 `_relevance` 时不传 `term_weights`，于是关系只过 `MIN_TERM_COVERAGE
   = 0.25` 这个平的门槛：5 个词的查询命中 2 个就算数。项目名每条知识都带，它分辨不出任何
   东西，却足以让一条知识被判为命中。项目事实和全部偏好都存成关系，所以这条路才是主路。

2. **预算不是按分数花的。** `pageKnowledgeSearch` 把各个查询的结果按**位置**轮流排
   （第 1 个查询的第 1 条、第 2 个查询的第 1 条……），和分数无关。页面装满就停。
   20 次调用里 6 次被截断，平均排出 4.45 条只送出 2 条。排第一的那条若又大又弱，它就把
   整页吃掉，后面分数更高的进不来——这就是「22 条里只给 1 条，还是不相关的那条」。

   这次基线里丢掉的标准答案是 0，因为虚构世界里标准答案基本都排第一。真实库里条目更多、
   更大，排序越靠后越容易被这条规则吃掉。

3. **一条命中约 1.7 KB，正文只有一句话。** `/v1/search` 返回的 `FactResult` 有约 50 个字段，
   其中 `utility_score`、`human_change_version`、`last_agent_viewed_at` 等排序根本不读。
   这是「6 次调用就被截断」的直接原因，也是 token 账单的大头。

4. **被标记「可能过时」的条目仍排在正确答案前面。** `sc-flagged-zh` 里
   `requires_attention: true` 的那条排第 1，正确的那条排第 2。`ATTENTION_FACTOR = 0.5`
   只把权重减半，权重在总分里只占一半，最终只扣掉 25%。

## 其他发现（没改）

- **一次调用里，低分的关系排在高分的实体前面。** 页面按「事实、实体、事实、实体」轮流装，
  不看分数。`sc-flagged-zh` 里被标「可能过时」的关系得 9 分，正确的实体得 11 分，AI 先读到
  前者。没有改，是因为标签重排返回的 `score` 是乘系数之前的分，按它排序会把标签重排的结果
  弄乱；而且各查询、事实和实体的分数量纲不同（见上文 ②），要改得先有可比的分数。
- **按需检索工具列出的 schema 不带任何上下界**（`chat-listing.js` 刻意去掉，理由是
  OpenCode code mode 会把每条界限渲染成 JSDoc）。所以 AI 看不到 `queries` 最多 10 个，
  发 11 个才收到 `-32602 ... maximum of 10 items`。这次把上限写进了工具说明的正文（「max 10」），并把同一句别处缩短，工具清单总字节反而少 3。
  rec#111 说的「5 个查询返回 500」已经不复现，5 个查询正常返回。
- **`search_knowledge_graph` 要 `personalSpaceId`，而 AI 只能从入口拿到它。** 入口被预算
  裁掉时，这个工具就没法调了。`search_current_project_knowledge` 收 `projectPath`——AI
  永远知道自己在哪——没有这个问题。两个工具的入门门槛不一样。
- **完整返回和被截断的返回，`retrieval_budget` 字段形状不同**：完整时只有
  `{limit_bytes, complete: true}`，截断时才有 `returned_items` / `total_items`。
  AI 要判断「我是不是拿全了」得处理两种形状。
- **`scope_policy` 的 6 个布尔值每次调用都重发**（约 230 B），对单次调用没有可操作的信息。

## 已知不准之处

- 37 条知识偏少；每个查询打出分的平均只有 4 条。
- 候选池按「和查询至少共享一个词、最多 `min(max(limit*8,40),100)` 条」近似 Graphiti 的混合检索，
  候选的次序也是虚构世界里的次序；关系分数里有一部分取决于这个次序。
- 不覆盖鉴权、Cypher 侧过滤、标签重排、向量与 RRF 融合（虚构世界不存向量，`standing_out`
  不出手，和在场向量条目不足 12 条的真实安装一样）。
- C 的耗时是打分阶段本身、37 条、同一个热进程里的数，只能当回归信号用；入口真实耗时的
  量法是 rec#126 的分段计时。
- 分语言、分类别的数字每格只有几题，只说方向。
