# Fuli 知识验收用例

本文档是后续人工检查 Fuli 是否符合预期的主清单。除特别标记为“人工验收”的项目外，
`KAC-01` 至 `KAC-09` 都由 `knowledge-live.js` 自动执行。

## 一、统一验收口径

### 1. 知识确认状态

| 技术值 | 中文含义 | 使用规则 |
| --- | --- | --- |
| `pending` | 待确认 | 可以按需检索；不能作为自动注入偏好；权威性最低 |
| `agent_confirmed` | 智能体已确认 | 达到有效使用门槛后自动晋级；可以使用，但低于人工确认 |
| `confirmed` | 已确认 | 由用户或权威来源确认；排序和冲突处理中的权威性最高 |

### 2. 有效使用门槛

- 仅检索、查看、进入上下文或自动注入偏好，不计为有效使用。
- 只有知识实际影响最终回答、实现或决策，并被标记为“引用”或“应用”，才计数。
- 同一知识、同一任务、同一使用类型、同一内容代次只能计数一次。
- 待确认知识累计 5 次有效使用，并且覆盖至少 3 个不同任务后，才可晋级为智能体已确认。
- 存在未解决冲突时，即使达到门槛也不得晋级。

### 3. 四象限口径

| 技术值 | 中文含义 |
| --- | --- |
| `known_known` | 记录时已经明确表达的知识 |
| `known_unknown` | 已经明确意识到、但仍未解决的问题或取舍 |
| `unknown_known` | 从行为、示例、原型或反应中推断出的隐性知识 |
| `unknown_unknown` | 在开放探索中暴露出的潜在盲点 |

四象限只描述知识最初如何被发现，不决定个人知识能否检索，也不直接改变检索排序。

## 二、运行环境验收

### ENV-01：当前工作区版本正在运行

类型：人工验收。

前置条件：

- 本地可能存在旧版本 Fuli 进程。
- 当前工作区已经完成构建。

操作步骤：

1. 停止记录中的旧 Fuli 管理界面进程。
2. 使用当前工作区代码重建并启动 Provider。
3. 启动当前工作区管理界面。
4. 检查管理界面、个人图谱和 Provider 健康状态。
5. 检查 Codex 与 Claude Code 的 Fuli MCP 注册是否指向当前工作区。

预期结果：

- `2727` 端口只有当前工作区进程监听。
- 个人图谱和 Provider 均处于可用状态。
- MCP 工具清单包含知识检索和知识使用记录工具。

### ENV-02：安装来源与当前运行来源可以明确区分

类型：自动化与人工联合验收。

前置条件：

- 仓库源码可用。
- 如需验证公开安装，机器已安装 npm 和受支持的 Node.js。

操作步骤：

1. 检查包清单中的 npm 包名、版本和命令入口。
2. 运行 npm 包体冒烟测试，把当前 tarball 安装到隔离的全局前缀。
3. 分别执行 `fuli --version`、`fl --version` 和 `fuli --help`。
4. 检查当前实际监听进程与 MCP 注册使用的启动文件。
5. 将“正在测试工作区源码”或“正在测试全局 npm 包”作为两种不同来源记录。

预期结果：

- npm 包名为 `fuli-context`，同时提供 `fuli` 和 `fl` 两个等价命令。
- 包体冒烟测试不读取或修改机器现有的全局 npm 安装。
- 当前运行来源可以追溯到工作区源码或 npm 全局包之一，不根据命令名或版本号猜测。
- 测试工作区未发布改动时，必须先重建、重启并按 ENV-01 验证当前工作区版本。

### CC-01：Claude Code 在真实验收前完成版本检查

类型：人工验收。

前置条件：

- 本机已经安装并登录 Claude Code。
- 可以访问 Claude Code 的官方更新通道。

操作步骤：

1. 记录当前 `claude --version`。
2. 查询官方最新稳定版本或执行 Claude Code 官方更新检查。
3. 只有存在更新时才更新现有安装。
4. 再次检查版本和安装健康状态。
5. 完成版本检查后才执行 AGT-02。

预期结果：

- 报告同时记录更新前版本、官方最新版本和更新后的实际版本。
- 已是最新版时不重复安装；需要更新时使用官方更新方式。
- 更新不修改 Fuli 源码、知识数据或测试文档。
- 版本检查或更新失败时，不把后续 Claude Code 调用链标记为已通过。

## 三、知识检索与项目继承

### KAC-01：待确认的父项目知识可以进入子项目检索

前置条件：

- 父项目存在一条 `pending` 部署知识。
- 该知识的继承模式允许向后代项目继承。
- 子项目通过明确的父子关系连接到父项目。

操作步骤：

1. 在子项目上下文中执行知识检索，并设置“包含待确认知识”。
2. 检查返回知识的定义项目、继承来源和作用域距离。
3. 再执行一次仅检索已确认知识的查询。

预期结果：

- 第一次检索命中父项目的待确认知识。
- 返回项标记为 `pending`，定义项目为父项目，继承距离为 1。
- 第二次检索不返回这条待确认知识。

### KAC-02：项目继承必须受到模式、关系和跳数约束

前置条件：

- 父项目分别存在“仅限本项目”“仅向指定项目继承”“向后代继承”三类知识。
- 项目关系包含父子关系、知识复用关系和普通关联关系。
- 项目链路包含父项目、子项目、孙级项目和曾孙级项目。

操作步骤：

1. 从子项目检索父项目知识。
2. 从兄弟项目检索只授权给子项目的知识。
3. 从孙级和曾孙级项目检索父项目知识。
4. 从子项目检索只存在于普通关联项目中的知识。

预期结果：

- “仅限本项目”的知识不会进入子项目。
- “仅向指定项目继承”的知识只进入被指定的子项目，不进入兄弟项目。
- 孙级项目可以通过两跳找到父项目知识。
- 曾孙级项目超过两跳，不能找到该父项目知识。
- 普通 `RELATED_TO` 关系不能扩张检索范围。
- 只有明确允许的 `PART_OF` 和 `USES_KNOWLEDGE_FROM` 关系参与继承。

### KAC-03：当前项目知识覆盖同稳定键的继承知识

前置条件：

- 父项目和子项目各有一条稳定键相同的知识。
- 父项目知识允许向子项目继承。

操作步骤：

1. 在子项目中按该稳定键对应的内容检索。
2. 检查最终返回项的定义项目、继承来源和作用域距离。

预期结果：

- 最终只保留一条有效知识。
- 返回子项目本地知识，而不是父项目继承知识。
- 继承来源为空，作用域距离为 0。

## 四、确认状态与使用计数

### KAC-04：5 次且跨 3 个任务后晋级智能体已确认

前置条件：

- 存在一条待确认知识。
- 当前内容代次没有未解决冲突。

操作步骤：

1. 在任务一中记录一次“引用”。
2. 重复记录同一次“引用”。
3. 在任务一中记录一次“应用”。
4. 在任务二中分别记录“引用”和“应用”。
5. 检查此时的使用次数、任务数和确认状态。
6. 在任务三中记录一次“引用”。

预期结果：

- 第二步被识别为重复事件，不增加计数。
- 前四个唯一事件覆盖 2 个任务，知识仍为待确认。
- 第五个唯一事件覆盖第 3 个任务后，知识晋级为 `agent_confirmed`。
- 效用分数大于 0。
- 置信分数高于初始值，但不得超过智能体确认上限 0.85。

### KAC-05：人工确认优先，内容变化重置智能体确认

前置条件：

- 同一查询可以同时命中人工确认知识和智能体已确认知识。
- 智能体已确认知识已有使用计数和双分数。

操作步骤：

1. 执行同时命中两条知识的检索。
2. 修改智能体已确认知识的正文内容。
3. 重新读取该知识。

预期结果：

- 人工确认知识排在智能体已确认知识之前。
- 内容修改后确认状态回到 `pending`。
- 内容代次增加 1。
- 有效使用次数和不同任务数归零。
- 效用分数归零，置信分数回到初始值 0.5。

### KAC-06：未解决冲突阻止自动晋级

前置条件：

- 待确认知识与另一条知识之间存在未解决冲突。

操作步骤：

1. 为待确认知识记录 5 次唯一有效使用。
2. 确保这些使用覆盖 3 个不同任务。
3. 检查晋级结果。

预期结果：

- 使用次数为 5，任务数为 3。
- 系统明确返回“未晋级”。
- 知识继续保持 `pending`。

## 五、偏好注入

### KAC-07：只注入全局偏好和当前精确项目偏好

前置条件：

- 存在一条已确认的个人全局偏好。
- 存在一条待确认的个人全局偏好。
- 父项目存在一条已确认的项目偏好。
- 全局偏好和父项目偏好使用相同偏好键，用于验证覆盖关系。

操作步骤：

1. 读取子项目的协作偏好。
2. 检查待确认偏好的使用次数。
3. 读取父项目的协作偏好。
4. 将待确认全局偏好通过 5 次且跨 3 个任务的有效使用晋级。
5. 再次读取子项目和父项目偏好。
6. 尝试创建一条可跨项目继承的个人偏好。

预期结果：

- 子项目自动获得已确认全局偏好。
- 待确认偏好不会自动注入，读取偏好也不会增加使用次数。
- 父项目只获得自身精确项目偏好；该偏好不会继承到子项目。
- 待确认全局偏好晋级后可以自动注入，但权威性仍低于人工确认。
- 父项目中相同偏好键的人工确认项目偏好覆盖智能体已确认全局偏好。
- 系统拒绝创建可跨项目继承的个人偏好，并且拒绝发生在写入之前。

## 六、四象限

### KAC-08：四象限只记录发现来源

前置条件：

- 四个原始象限各存在一条内容等价、确认状态相同的知识。

操作步骤：

1. 使用同一查询检索四条知识。
2. 比较四条知识的检索分数。
3. 尝试修改其中一条知识的原始象限。
4. 只修改该知识的当前象限。

预期结果：

- 四条知识都可以检索。
- 四条知识的分数相同，原始象限不参与个人检索排序。
- 修改原始象限被拒绝。
- 当前象限可以变化，但原始象限保持不变。
- 当前分类变化后，该知识回到待确认状态。

## 七、查询性能与边界

### KAC-09：当前项目查询保持有界

前置条件：

- 子项目存在可命中的本地或继承知识。

操作步骤：

1. 连续执行 12 次相同的子项目有界查询。
2. 每次检查实际声明的个人项目范围。
3. 统计中位数、百分之九十五分位数和最大耗时。

预期结果：

- 每次查询只声明当前子项目，不自动携带无关项目。
- 当前开发机的百分之九十五分位耗时低于 2 秒故障预算。
- 输出包含样本数、中位数、百分之九十五分位数和最大耗时。

## 八、MCP 模型可见结果

### MCP-01：命中知识不能被上下文预算整体裁掉

自动化入口：

```sh
node --test test/mcp-integration.test.js
```

预期结果：

- 来源标记显示命中。
- 模型可见结果包含知识正文摘要。
- 模型可见结果包含 `confirmation_status` 和 `confidence_score`。
- 整体返回不超过 32 KiB。
- 未命中时仍返回明确的顶部未命中标记和下一步检索指引。

### MCP-02：项目写入必须经过匹配且一次性的预览授权

自动化入口：

```sh
node --test test/mcp-integration.test.js
```

操作步骤：

1. 不预览，直接尝试项目写入。
2. 提交包含模式、目标项目、关系和变更内容的完整写入意图，预览该动作。
3. 使用返回的预览令牌，但修改目标项目后再尝试写入。
4. 恢复与预览完全一致的动作并执行写入。
5. 重复使用同一个预览令牌。

预期结果：

- 第一步在进入 Provider 之前被拒绝，没有数据变化。
- 预览只验证完整写入意图，不写入数据，并返回短期预览令牌。
- 令牌与完整动作不匹配时写入被拒绝，令牌仍然可用于原动作。
- 完全匹配的动作只成功一次。
- 重复使用同一个预览令牌被拒绝。
- 人工管理界面的直接操作不经过这条智能体 MCP 授权边界。

### MCP-03：未命中来源标记只展示一次

自动化入口：

```sh
node --test test/fuli-source-marker.test.js test/mcp-integration.test.js
```

操作步骤：

1. 执行一次确定不会命中的知识检索。
2. 检查 `noMatchSourceMarker.leadMarkdown`。
3. 检查 `noMatchSourceMarker.markdown`。
4. 按 MCP 指令组装最终回答。

预期结果：

- 回答顶部只显示一次“FULI · 已检索，未命中”链接。
- `noMatchSourceMarker.markdown` 是空字符串。
- 回答底部不再出现“FULI 来源 · 未命中”或“打开 Fuli”的重复页脚。
- 有支持性命中时仍保留正常的顶部标记和底部来源列表。

## 九、真实智能体验收

### AGT-01：Codex 调用链

类型：人工验收。

### AGT-02：Claude Code 调用链

类型：人工验收。

执行 AGT-02 前必须先通过 CC-01。

两项使用相同的只读提示词：

```text
这是一次只读的 Fuli MCP 回归验收。不要修改任何文件或数据。
第一步调用 Fuli 的协作偏好读取工具，当前工作目录作为项目路径。
第二步调用 Fuli 的知识检索工具，查询“四象限作为发现来源标签而非个人检索权重”，
复用第一步返回的个人空间和当前项目，限制返回 1 条，并包含待确认知识。
最后只报告调用顺序、是否命中、知识正文摘要和确认状态；不要猜测。
```

预期结果：

1. 工具事件顺序为“读取协作偏好”后“检索知识图谱”。
2. 第二次调用复用第一次解析出的个人空间和当前项目，不硬编码用户标识。
3. 检索显示命中。
4. 智能体能够复述返回知识的正文摘要。
5. 智能体能够报告明确的确认状态。
6. 整个过程没有尝试调用任何写入工具；只读任务即使因参数校验而没有落库，只要尝试调用过
   写入工具，也按失败处理。

真实智能体验收依赖客户端登录态、模型服务和本机 MCP 配置，因此不放入默认持续集成。

## 十、CLI 分发、更新与界面小图标

### CLI-01：`fuli update` 安全更新全局 npm 安装

自动化入口：

```sh
node --test test/update-command.test.js test/setup-options.test.js
npm run test:package
```

操作步骤：

1. 取消一次需要确认的更新。
2. 使用 `--yes` 执行模拟更新，并传入自定义数据目录、端口和启动选项。
3. 模拟 npm `latest` 低于当前工作区 CLI。
4. 模拟 npm 版本检查失败、旧服务无法安全停止、npm 安装失败和新版 `setup` 失败。
5. 模拟 npm 最新版本与当前版本相同。
6. 检查 README 的 CLI 命令表、更新说明和恢复命令。

预期结果：

- 取消更新时不停止服务，也不启动 npm 安装。
- npm 版本检查发生在停止服务之前；检查失败时不改变本地服务或安装。
- 当前 CLI 高于 npm `latest` 时拒绝降级，不停止服务，也不安装旧包。
- 更新先安全停止旧服务，再安装 `fuli-context@latest`。
- 安装完成后直接使用新包中的 CLI 执行 `setup --yes`，并保留用户传入的 setup 选项。
- 无法确认旧服务已停止时，在 npm 安装前终止。
- npm 或新版 setup 失败时明确说明知识数据未删除，并给出可复制的恢复命令。
- 已是最新版时仍可刷新 Agent 接入和 Skills。
- README 同时说明 `fuli`、`fl`、服务生命周期、setup、update 和卸载命令。

### WEB-01：使用包内浏览器小图标，不向回答插入大图

自动化入口：

```sh
node --test test/server-context-api.test.js test/server-request-boundary.test.js
```

操作步骤：

1. 构建 Web UI 并通过 HTTP 请求 `/favicon.ico`。
2. 检查状态码、内容类型和 PNG 文件头。
3. 检查回答来源标记没有插入图片标签或内联大图。
4. 在 npm 包体冒烟测试中再次验证已打包 Web UI。

预期结果：

- `/favicon.ico` 返回包内 Fuli Logo，内容类型为 `image/png`。
- 图标来自发布包，不依赖某一台开发机的绝对路径。
- 回答正文和来源标记不插入大 Logo 图片。
- 该能力只控制 Fuli Web 页面的浏览器图标；Codex 客户端在链接前显示的地球图标由
  Codex 自身渲染，不把替换该客户端图标作为 Fuli 的通过条件。
