# 召回成功率基线

`npm run measure:recall-rate`，2026-11-23。虚构世界 32 条知识、2 个项目、1 个个人空间；
不连 Neo4j、不用嵌入模型、不调任何模型。量法和它看不到的东西见
`acceptance/recall-rate/README.md`。

下面「基线」= `origin/main` 79c655ad，「修复后」= 本分支三处修复之后，同一批用例、同一台
机器、同一个解释器。

## 一、入口自动带的偏好

| | |
|---|---:|
| 任务数 | 6 |
| 该带的带上 | 12 / 12（100%） |
| 不该带的带上 | 1 / 9（11.1%） |
| 其中范围限定的误带 | 0 / 8（0%） |
| 每个任务平均带几条 | 5.33 |

结构化的范围限定（`workKind`、`workflow`）是准的：8 次「不该带」一次没漏。唯一的误带是
`pref-prd-only`——它的适用范围「仅适用于 PRD 评审」只写在正文里，没有结构化限定，FULI
没有任何依据过滤它。这正是 rec#111（11-22）里那条「仅适用于某类业务需求」被当成 PRD
评审标准的同一个缺口：**不是匹配算错，是范围根本没被记成可匹配的东西**。

## 二、入口自动召回

| | |

| 不该召回的召回 | 0 / 19（0%） |

命中率不低，精确率很低：**送到 AI 面前的条目里，接近六成和这个任务无关**。
偏题的分布很集中：

| 任务 | 送出的偏题条目 |

| eb-principle（问产品原则） | 错误码、值班频道、发布流程 |
| eb-error-code（加错误码） | 评审负责人、发布流程 |
| eb-release（发布） | 错误码、值班频道 |
| eb-staging-where（问地址） | 发布流程、预发布端口 |
| eb-port / eb-settlement / eb-mixed / eb-en-where | 发布流程（反复出现） |

同一批条目反复出现在互不相关的任务里，原因在第三节。

## 三、按需检索

| | |
|---|---:|
| 调用次数 | 20 |
| 标准答案出现在结果里 | 22 / 22（100%） |
| 前 5 条里有标准答案的调用 | 20 / 20（100%） |
| MRR | 0.908 |
| 前 5 条里的干扰项 | **5** |
| 预算截断丢掉的标准答案 | 0 |
| 被预算截断的调用 | **6 / 20** |
| 平均送出 / 排出的条目 | **2 / 4.45** |
| 每次平均体积 | 4787 B / 约 1217 token |

按语言分：

| 查询语言 | 标准答案 | 前 5 命中 | MRR | 前 5 干扰项 |
|---|---:|---:|---:|---:|
| 中文 | 11/11 | 10/10 | 0.883 | **5** |
| 英文 | 6/6 | 5/5 | 0.867 | 0 |
| 中英混合 | 5/5 | 5/5 | 1.0 | 0 |

**排序本身在聚焦查询上是好的**（MRR 0.908，标准答案全部进了前 5）。问题全在两处：

1. **查询里只要带项目名，这个项目的东西就全都算命中。**
   `sc-named-project-zh`（查询「潮池账本 发布流程」「潮池账本 打 tag 命令」）排出 **22 条**，
   前 5 条里有 3 条是明确标注的干扰项，最后只送出 3 条。
   `sc-principle-zh`（查询「潮池账本 产品原则」等 4 句）排出 16 条，第 2 条是无关的
   「界面文案中英双语」偏好——和 rec#111 11-10 表格里那条 1.85 分的宣传偏好是同一回事。

   原因确定了：`_relevance` 里按「这个词能分辨多少候选」加权的那套（`_term_weights`、
   `_too_common`，注释里直接写着「rec#111」）**只接在实体这条路上，关系这条路没接**。
   `_edge_relevance` 调 `_relevance` 时不传 `term_weights`，于是关系只过 `MIN_TERM_COVERAGE
   = 0.25` 这个平的门槛：5 个词的查询命中 2 个就算数。项目名每条知识都带，它分辨不出任何
   东西，却足以让一条知识被判为命中。项目事实和全部偏好都存成关系，所以这条路才是主路。

2. **预算不是按分数花的。** `pageKnowledgeSearch` 把各个查询的结果按**位置**轮流排
   （第 1 个查询的第 1 条、第 2 个查询的第 1 条……），和分数无关。页面装满就停。
   20 次调用里 6 次被截断，平均排出 4.45 条只送出 2 条。排第一的那条若又大又弱，它就把
   整页吃掉，后面分数更高的进不来——这就是「22 条里只给 1 条，还是不相关的那条」。

   这次基线里丢掉的标准答案是 0，因为虚构世界里标准答案基本都排第一。真实库里条目更多、
   更大，排序越靠后越容易被这条规则吃掉。

3. **一条命中约 1.7 KB，正文只有一句话。** `/v1/search` 返回的 `FactResult` 有约 50 个字段，
   其中 `utility_score`、`human_change_version`、`last_agent_viewed_at` 等排序根本不读。
   这是「6 次调用就被截断」的直接原因，也是 token 账单的大头。

4. **被标记「可能过时」的条目仍排在正确答案前面。** `sc-flagged-zh` 里
   `requires_attention: true` 的那条排第 1，正确的那条排第 2。`ATTENTION_FACTOR = 0.5`
   只把权重减半，权重在总分里只占一半，最终只扣掉 25%。

## 修复了什么

1. **关系也按「这个词能分辨多少候选」加权**（`_edge_relevance` 传 `term_weights`）。
   B 的精确率 0.417 → 0.588，偏题条目 14 → 7；C 的前 5 干扰项 5 → 3，被截断的调用 7 → 2。
2. **页面预算按分数花**（`pageKnowledgeSearch` 同一轮内按分数排序，轮转不变）。
   答案在最后一个查询、前面几个查询很宽的那次调用，原来把答案挤掉了（丢 1 条），现在不丢。
3. **返回体不再带 null 字段**（只改两个检索工具交给 Agent 的页面）。
   C 每次 4895 B → 4097 B（约 1245 → 1045 token），一次调用能多装一条结果。

还没修、证据已经在上面的：第一节的正文范围限定（需要把适用范围结构化，改的是捕获侧）、
第三节第 4 条的「可能过时」权重、以及下面「其他发现」。

## 耗时

修复 1 多了一遍 IDF 扫描。单独量（100 个候选，Graphiti 的候选上限；5 个查询，15 次取中位数）：

| | 每个查询的打分阶段 |
|---|---:|
| 基线 | 2.70 ms |
| 修复后 | 4.61 ms |

多 1.9 ms。rec#126 实测一次 `/v1/search` 在 #924 之后是 863 ms，所以这是约 0.2%，
在噪声里。**没有在真实实例上端到端量过**：这台机器上 Docker 没起，唯一的 Neo4j 是已安装
的那个 FULI 正在用的，不能动。要端到端量（也顺便校验这套量法和真实 `/v1/search` 排序
是否一致），按 rec#126 11-13 那条评论的做法：把 `native-runtime` 里的 Neo4j 5.26.28
发行包解到另一个目录，换端口和数据目录起第二个实例。这是这份基线最大的待办。
顺带发现：`_term_weights` 和 `_relevance` 对同一条记录各做一次分词，
省掉重复这一半是现成的优化，但它同时影响实体那条路和已冻结的 `recall_weight_benchmark`，
不在这次范围里。

## 其他发现（没改）

- **一次调用里，低分的关系排在高分的实体前面。** 页面按「事实、实体、事实、实体」轮流装，
  不看分数。`sc-flagged-zh` 里被标「可能过时」的关系得 9 分，正确的实体得 11 分，AI 先读到
  前者。没有跟着修复 2 一起改，是因为标签重排返回的 `score` 是乘系数之前的分，
  按它排序会把标签重排的结果弄乱；要改得先理清这一点。
- **按需检索工具列出的 schema 不带任何上下界**（`chat-listing.js` 刻意去掉，理由是
  OpenCode code mode 会把每条界限渲染成 JSDoc）。所以 AI 看不到 `queries` 最多 10 个，
  发 11 个才收到 `-32602 ... maximum of 10 items`。这次把上限写进了工具说明的正文。
  rec#111 说的「5 个查询返回 500」已经不复现，5 个查询正常返回。
- **`search_knowledge_graph` 要 `personalSpaceId`，而 AI 只能从入口拿到它。** 入口被预算
  裁掉时，这个工具就没法调了。`search_current_project_knowledge` 收 `projectPath`——AI
  永远知道自己在哪——没有这个问题。两个工具的入门门槛不一样。
- **完整返回和被截断的返回，`retrieval_budget` 字段形状不同**：完整时只有
  `{limit_bytes, complete: true}`，截断时才有 `returned_items` / `total_items`。
  AI 要判断「我是不是拿全了」得处理两种形状。
- **`scope_policy` 的 6 个布尔值每次调用都重发**（约 230 B），对单次调用没有可操作的信息。

## 已知不准之处

- 32 条知识偏少，IDF 可用的信号有限；真实库条目更多时，第三节第 1 条的影响只会更大，不会更小。
- 候选生成用固定顺序代替 Graphiti 的混合检索，只影响同一分数带内的次序。
- 不覆盖鉴权、Cypher 侧过滤、标签重排、向量与 RRF 融合（虚构世界不存向量，`standing_out`
  不出手，和在场向量条目不足 12 条的真实安装一样）。
- 第三节的耗时是打分阶段本身、32 条、同一个热进程里的数，只能当回归信号用；入口真实耗时的
  量法是 rec#126 的分段计时。
- 中文/英文/混合三组各只有 7/6/7 次调用，分语言的数字只说方向。
