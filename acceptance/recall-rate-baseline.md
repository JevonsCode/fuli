# 召回成功率基线

`npm run measure:recall-rate`，2026-11-24 重量（`origin/main` 444814cf）。虚构世界 37 条知识
（其中 5 条没有手写检索词）、2 个项目、1 个个人空间；不连 Neo4j、不用嵌入模型、不调任何模型，
本机约 2 秒。量法和它看不到的东西见 `acceptance/recall-rate/README.md`。

## 这把尺子能说明什么

- **竞争很少。** 按需检索每个查询平均有 14.1 条参与打分（关系先按「和查询至少共享一个词」筛过，
  实体是范围内全部），其中 4.1 条打出分；每次调用平均送出 2.4 条。入口每个任务送出 1.8 条。
- **题是照着答案写的。** 原有 21 次调用里，标准答案大多手写了和查询逐字对得上的检索词；
  把检索词全部去掉，常规题的标准答案送达从 23/23 降到 21/23（见下文「检索词贡献了多少」）。
- **镜像不是完整的检索。** Graphiti 的混合检索（分词、按意思找的候选、它自己的次序）、向量与
  RRF 融合、鉴权、Cypher 侧过滤、标签重排都不在里面；候选池是按「共享一个词」近似的。
- 所以「满分」只说明：真代码（入口的查询生成、过滤、预算；搜索页的预算；Provider 的打分函数）
  在这个小世界上和写好的答案一致，以及一处改动让这些数字往哪边走。它**说明不了真实库里的召回率**。

## 新题：四类难例

每类单独统计，也计入总表。C 列是「标准答案送达 / 打出分 / 前 5 命中」，精确率 = 送出条目里
标准答案的比例（口径和 B 一样严，不是标准答案都算偏题）。

| 类别 | 题数 | main | 只有改动 ①（PR 原样） | 只有改动 ①（修正后） | 全部（PR 原样） | 全部（修正后） |
|---|---:|---|---|---|---|---|
| 近义不同词（上线↔发布、值守↔值班） | C 4 · B 1 | C 0/4 · 0 · 0；B 1/1 | 同 main | 同 main | 同 main | 同 main |
| 只靠项目名共享 | C 5 · B 1 | C 1/5 · 5 · 3，精确率 0.067；B 0/1 | **C 0/5 · 0 · 0**；B 1/1 | C 2/5 · 5 · 4，0.133；B 0/1 | **C 0/5 · 0 · 0**；B 1/1 | C **3/5 · 5 · 4**，0.150；B 0/1 |
| 两个项目里同名 | C 4 | C 4/4，MRR 1，0.364 | C 4/4，MRR 0.875 | C 4/4，MRR 0.875 | C 4/4，MRR 0.875，0.333 | C 4/4，MRR 0.875，0.308 |
| 没有手写检索词 | C 3 · B 1 | C 3/3，0.6；B 1/1 | C 3/3；**B 0/1** | C 3/3；B 1/1 | C 3/3；**B 0/1** | C 3/3，0.6；B 1/1 |

- **近义不同词**在没有向量的镜像里本来就召回不了：没有共享的词，也没有能接上的检索词。这是
  已知缺口，要靠向量（或记录时写对检索词）补，不在这里硬编同义词表。
- **只靠项目名共享**正是评审指出的那一类：PR 原样的改动 ① 把这 5 题全部判成 0 分（main 时都能
  以低分召回），所以修正了，见下一节。
- **同名**这类，改动 ① 的两个版本都让 `sc-same-named-other`（在潮池账本里问「灯笼鱼官网 发布
  流程」）的答案从第 1 名掉到第 2 名：项目名加权后分量变轻，当前项目那条（检索词「发布」整词
  命中）的覆盖率随之变高，压过了点名的另一个项目那条（范围系数 0.85）。两条都送达了，只是次序。
- **没有检索词**这类，PR 原样的改动 ① 让入口漏了 `eb-backup`（「潮池账本的备份留多久」：
  「备份」是区分词，但跨词拼出来的字对「本备」「份留」「留多」按半权计入分母，加权覆盖率不到
  0.33，判为 0 分），修正后回来了。

## 改动 ① 最终保留成什么样

**区分度权重只用来排序，不再用来把原本过门槛的关系判成 0 分。** 一条关系如果在加权下只命中了
常见词（比如只有项目名），它仍按加权之前的门槛算命中，但分数只保留加权前的 5%
（`COMMON_TERMS_SHARE`），排在所有靠有区分度的词命中的条目后面。实体那条路不变（从 rec#111
起就会把这种条目判为 0 分）。

为什么不是别的做法，三种都量过（全部改动、修正后的 ② 和 ③ 不变，只换 ①）：

| ① 的做法 | B 精确率 | C 常规题 MRR / 前 5 干扰项 | 只靠项目名：送达 / 打出分 / 前 5 |
|---|---:|---|---|
| main（不加权） | 0.448 | 0.877 / 4 | 1/5 · 5 · 3 |
| PR 原样：加权，只命中常见词判 0 分 | **0.619** | 0.885 / **3** | **0/5 · 0 · 0** |
| 只在本次搜索没有任何条目靠区分词命中时，退回不加权 | 0.448 | 0.885 / 3 | 2/5 · 4 · 2 |
| **只排序，不判 0 分（采用）** | 0.448 | 0.885 / 4 | **3/5 · 5 · 4** |

- B 精确率的提升（0.448 → 0.619）**全部来自**把「只命中项目名」的关系判成 0 分：入口第一个查询
  就是任务原句（如「潮池账本这版改完」），只和项目名共享，main 时会带出整个项目。而「只靠项目名
  共享」的新题，标准答案恰恰也是这样的条目。只看词面，两者分不开：要么都留，要么都丢。
- 「退回」那种做法还会漏一题（`sc-name-online`：查询里的「线上」恰好在值班频道那条里，
  于是只有它算命中，发布流程被判 0 分），不满足「不比 main 差」。
- 采用的做法：召回在四类新题上都不比 main 差；保住的是排序（C 常规题 MRR 0.877 → 0.885，
  只靠项目名那类前 5 命中 3 → 4）；**没保住的是 B 的精确率**，回到 main 的 0.448。
- 要在入口侧把这部分精确率拿回来，入口得能分辨「只命中常见词」的条目；用分数门槛不行（有向量的
  安装里分数是 RRF，量纲不同），需要 Provider 明确标出来。这改的是返回格式，不在本 PR 里做。

## 改动 ② 跨查询怎么排

同一轮（每个查询各出第 n 条）里，按「这条的分数占本查询同类结果第一名的比例」排，不再直接比
原始分数。有向量的安装里融合分数是 RRF（约 0.016–0.033），只走词法的查询在 4–12，原始分数一比，
词法查询永远排前面。按比例排的结果：每个查询的第一条都是 1，按提问的顺序；之后谁更接近自己那一
组的第一名，谁先上。排序只依赖同一批结果，翻页前后一致。基准没有向量，看不到这个差别（PR 原样
和修正后在基准上数字相同）。

## 改动 ③ 去掉 null 字段

只改两个检索工具交给 Agent 的页面。C 每次体积主要靠它下降，也让同一页装得下更多条目（预算丢掉的
标准答案 5 → 2）。

## 耗时

改动 ① 多了一遍 IDF 扫描，修正后对「加权下 0 分」的条目再按不加权算一次。单独量（100 个候选，
Graphiti 的候选上限；5 个查询，15 次取中位数）：main 1.4 ms、PR 原样 2.2 ms、修正后 3.3 ms
（每个查询的打分阶段）。rec#126 实测一次 `/v1/search` 在 #924 之后是 863 ms，多 1.9 ms 约 0.2%。
没有在真实实例上端到端量过（不能动正在用的 Neo4j）。

按语言分：

|---|---:|---:|---:|---:|

**排序本身在聚焦查询上是好的**（MRR 0.908，标准答案全部进了前 5）。问题全在两处：

1. **查询里只要带项目名，这个项目的东西就全都算命中。**
   `sc-named-project-zh`（查询「潮池账本 发布流程」「潮池账本 打 tag 命令」）排出 **22 条**，
   前 5 条里有 3 条是明确标注的干扰项，最后只送出 3 条。
   `sc-principle-zh`（查询「潮池账本 产品原则」等 4 句）排出 16 条，第 2 条是无关的
   「界面文案中英双语」偏好——和 rec#111 11-10 表格里那条 1.85 分的宣传偏好是同一回事。

   原因确定了：`_relevance` 里按「这个词能分辨多少候选」加权的那套（`_term_weights`、
   `_too_common`，注释里直接写着「rec#111」）**只接在实体这条路上，关系这条路没接**。
   `_edge_relevance` 调 `_relevance` 时不传 `term_weights`，于是关系只过 `MIN_TERM_COVERAGE
   = 0.25` 这个平的门槛：5 个词的查询命中 2 个就算数。项目名每条知识都带，它分辨不出任何
   东西，却足以让一条知识被判为命中。项目事实和全部偏好都存成关系，所以这条路才是主路。

2. **预算不是按分数花的。** `pageKnowledgeSearch` 把各个查询的结果按**位置**轮流排
   （第 1 个查询的第 1 条、第 2 个查询的第 1 条……），和分数无关。页面装满就停。
   20 次调用里 6 次被截断，平均排出 4.45 条只送出 2 条。排第一的那条若又大又弱，它就把
   整页吃掉，后面分数更高的进不来——这就是「22 条里只给 1 条，还是不相关的那条」。

   这次基线里丢掉的标准答案是 0，因为虚构世界里标准答案基本都排第一。真实库里条目更多、
   更大，排序越靠后越容易被这条规则吃掉。

3. **一条命中约 1.7 KB，正文只有一句话。** `/v1/search` 返回的 `FactResult` 有约 50 个字段，
   其中 `utility_score`、`human_change_version`、`last_agent_viewed_at` 等排序根本不读。
   这是「6 次调用就被截断」的直接原因，也是 token 账单的大头。

4. **被标记「可能过时」的条目仍排在正确答案前面。** `sc-flagged-zh` 里
   `requires_attention: true` 的那条排第 1，正确的那条排第 2。`ATTENTION_FACTOR = 0.5`
   只把权重减半，权重在总分里只占一半，最终只扣掉 25%。

## 其他发现（没改）

- **一次调用里，低分的关系排在高分的实体前面。** 页面按「事实、实体、事实、实体」轮流装，
  不看分数。`sc-flagged-zh` 里被标「可能过时」的关系得 9 分，正确的实体得 11 分，AI 先读到
  前者。没有跟着修复 2 一起改，是因为标签重排返回的 `score` 是乘系数之前的分，
  按它排序会把标签重排的结果弄乱；要改得先理清这一点。
- **按需检索工具列出的 schema 不带任何上下界**（`chat-listing.js` 刻意去掉，理由是
  OpenCode code mode 会把每条界限渲染成 JSDoc）。所以 AI 看不到 `queries` 最多 10 个，
  发 11 个才收到 `-32602 ... maximum of 10 items`。这次把上限写进了工具说明的正文（「max 10」），并把同一句别处缩短，工具清单总字节反而少 3。
  rec#111 说的「5 个查询返回 500」已经不复现，5 个查询正常返回。
- **`search_knowledge_graph` 要 `personalSpaceId`，而 AI 只能从入口拿到它。** 入口被预算
  裁掉时，这个工具就没法调了。`search_current_project_knowledge` 收 `projectPath`——AI
  永远知道自己在哪——没有这个问题。两个工具的入门门槛不一样。
- **完整返回和被截断的返回，`retrieval_budget` 字段形状不同**：完整时只有
  `{limit_bytes, complete: true}`，截断时才有 `returned_items` / `total_items`。
  AI 要判断「我是不是拿全了」得处理两种形状。
- **`scope_policy` 的 6 个布尔值每次调用都重发**（约 230 B），对单次调用没有可操作的信息。

## 已知不准之处

- 37 条知识偏少，IDF 可用的信号有限；每个查询打出分的平均只有 4 条。
- 反过来的风险：改动 ① 让「只命中常见词」的关系排到最后。这批题里没有因此丢掉送达的标准答案
  （只靠项目名那类 main 1/5 → 3/5），但题少。实体那条路从 rec#111 起会把这种条目直接判为 0 分，
  这次没改它；真实库上值得再看一轮。
- 候选池按「和查询至少共享一个词、最多 `min(max(limit*8,40),100)` 条」近似 Graphiti 的混合检索。
  加权的分母就是这个池，所以池不同，哪个词算常见词也会不同——不只是同一分数带内的次序。
- 不覆盖鉴权、Cypher 侧过滤、标签重排、向量与 RRF 融合（虚构世界不存向量，`standing_out`
  不出手，和在场向量条目不足 12 条的真实安装一样）。
- C 的耗时是打分阶段本身、37 条、同一个热进程里的数，只能当回归信号用；入口真实耗时的
  量法是 rec#126 的分段计时。
- 分语言、分类别的数字每格只有几题，只说方向。
