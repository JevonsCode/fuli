# 多智能体关系网验收

本验收中的 A–E 项目、偏好、步骤和编号全部是 **MOCK（合成）数据**，不代表真实项目事实。

## 产品理念

FULI 验证的是人在持续与 Agent 协作中形成的关系网。关系节点可以连接本地文档、外部知识源、项目、决定、工作步骤和其他知识库，但文档存储本身不是产品目标。

关系网应逐渐沉淀个人品味、个性与判断偏好，并保留人的最终决定权：

- 多个项目重复出现的共同核心可以成为更高作用域候选；
- 相似度、使用次数、项目距离、时效、确认权威和负面证据分别影响候选排序；
- 分数不能自行改变偏好作用域或越过冲突与人工确认；
- 重复出现的 `X → Y` 可以成为下一步建议，但首次转为长期自动执行前必须征得用户同意。

## 公开验收边界

1. Codex 从 MOCK（合成）文档沉淀 A、B 的共享上下文、C/D/E 的项目偏好和 `X → Y` 事件证据。
2. Cursor 在空工作区中只通过 FULI 检索，验证多父继承、关联项目不自动扩张以及下一步建议。
3. Claude Code 在另一个空工作区中重新检索相同关系，验证跨 Agent 可用性和人工确认门。
4. MOCK（合成）人工确认后再启动一个全新的 Claude Code 会话，验证长期低风险授权能跨会话读取，
   而高风险动作仍保留逐次确认门。
5. FULI 的确定性 API 检查共同核心候选是否可发现、是否保持只读，以及人的候选绑定决定是否保留局部限定与来源。

## Graphiti 捕获契约

- `known_known` 可以直接保存来源明确、已确认的文档事实。
- `known_unknown`、`unknown_known`、`unknown_unknown` 都必须提供
  `reasoningSummary`，说明为什么这是推断、疑问或探索性节点，而不是已确认事实。
- 重复 `X → Y` 属于 `unknown_known` 行为归纳，因此只能先保存为 `pending` 关系；
  Agent/宿主适配器每次只能提交一个真实 step observation，次数必须由 Provider 的不同
  `Episodic` 证据计算，不能信任 Agent 自报的 `occurrenceCount`。
- 候选分数只能决定是否建议。候选版本、一次性人工预览和持久授权是独立的硬门；
  高风险发送、删除、发布、支付和外部写入即使有长期规则也仍需逐次确认。
- Provider 的结构化 422 校验错误必须向调用 Agent 暴露安全的字段路径和原因，不能只返回
  “Graphiti provider request failed”。

## 预期判定

- `travel-d` 能取得 `NETWORK-A-GUIDE-101` 与 `NETWORK-B-GUIDE-202`，并保留两条来源路径。
- `related-c` 不自动取得 D 的项目知识，只能提示扩展搜索。
- C、D 与 E 的共同核心可以提高候选优先级，但不能自动成为全局偏好。
- “注释使用中文”只属于 E，不能被提升为所有项目的默认规则。
- D/E 的共同核心只有在人确认目标为父项目 A 后，才创建一条 A 的 `descendants` 偏好；
  D/E 原文、来源与 E 的中文限定继续保留，其他 A 子项目可通过明确继承路径使用共同核心。
- 人确认共同核心适用于个人全局后，应创建新的全局断言并保留 C/D/E 原文、来源和 E 的中文限定；
  旧版本候选或重放过的一次性确认不得再次写入。
- `NETWORK-STEP-X-606` 完成后可以推荐 `NETWORK-STEP-Y-707`，但不能在没有人工同意时自动执行。

本验收覆盖跨 Agent 的 observation、持久聚合、推荐和授权原语；它不把“已能透明监听任意
Codex/Cursor/Claude 外部工具调用”列为已完成能力。没有安装宿主 telemetry 适配器时，仍需
Agent 或集成方显式提交本次完成的 step observation。
